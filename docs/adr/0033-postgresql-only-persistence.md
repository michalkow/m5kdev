# PostgreSQL-only persistence with pgvector

The target architecture replaces Turso/libSQL entirely with PostgreSQL for m5kdev application persistence and Mastra persistence, using pgvector for vector storage. The scope includes the Kernel, optional modules, Starter, CLI scaffolding, tests, deployment configuration, and active documentation; historical references may remain when clearly superseded. PostgreSQL-only persistence and consolidated vector storage are architectural constraints, not an invitation to add unrelated product changes.

Starter will include durable Mastra storage and conversation Memory. This adds persistence absent from the current Starter; Mastra composition remains app-owned, and Conversation history remains a Mastra Thread rather than `chats.conversation` ([ADR-0007](0007-mastra-thread-over-chats.md)). Existing tenancy and authorization boundaries remain unchanged.

## Consumer migration contract

Provide framework developers with an AI-agent migration prompt covering every framework table and every consumer app-owned table. The prompt must require a field-by-field assessment of serialized data and conversion to native PostgreSQL JSON or array representations where appropriate, including corresponding repository queries, serialization, validation, and tests. It must distinguish structured documents, homogeneous collections, and relational associations rather than converting every JSON-looking text field or relationship into an array.

This prompt is an upgrade deliverable, not authorization to discard existing data or a universal production cutover script. Preserve existing data by default; destructive resets require the consuming developer to explicitly declare the environment disposable. Require backups, explicit source-to-target mappings, validation, and a rollback plan before production cutover. Zero downtime is not a universal requirement. Database commands stay Kernel-owned and HTTP-free, while schema composition and migration history remain app-owned ([ADR-0005](0005-kernel-owns-database-commands.md)); migration files are generated by the maintainer, not the agent.

## Database Ownership and Deployment

Use one database per app/environment, with separate schemas and explicit ownership for application tables, Mastra storage, and vectors. App migrations own framework and app tables; Mastra owns its storage structures. Separate connection configuration is supported without requiring separate databases. Preserve native `mastra_` naming wherever supported; schema isolation and table prefixes complement each other, rather than replacing either with the other or patching vendor internals to force names.

The deployment contract is provider-neutral and may require PgBouncer and pgvector. Runtime uses the PgBouncer connection; the environment also supplies a direct PostgreSQL connection for Drizzle migration functions. Expose both connection roles explicitly, allow identical URLs where appropriate, and target transaction-pooling compatibility. Repositories share the application pool rather than constructing their own pools. Exact driver and dependency versions remain subject to compatibility verification.

`DATABASE_URL` supplies the runtime/PgBouncer connection; `DATABASE_DIRECT_URL` supplies Drizzle migrations and administrative initialization. Migration operations require the direct setting and do not silently fall back to the runtime connection. Both settings remain server-only.

Local development and CI use real PostgreSQL with pgvector rather than a SQLite substitute. Provision pgvector and run application migrations explicitly before startup. Run required Mastra storage initialization as a separate deployment step using its supported lifecycle; ordinary startup checks readiness and fails clearly rather than silently migrating application tables. Driver, pooling, and adapter lifecycle compatibility must be verified before implementation relies on them.

Default schema names are `app`, `mastra`, and `vectors`, configurable at app composition roots. App reset and migration operations must respect those ownership boundaries and must not implicitly destroy Mastra history.

## Vector Scope

Preserve the current embedding/upsert use case and add only the pgvector configuration and setup needed to operate it. Embedding model, dimensions, and distance metric are explicit and app-owned; validate dimensions. A new retrieval API and approximate-index tuning are outside this migration's scope.

## Native Types and Compatibility

Use JSONB for structured documents, native arrays for genuine homogeneous scalar collections, native booleans, and timezone-aware timestamps for instants. Keep existing identifiers as text and preserve relational association tables. Preserve API payload contracts and explicitly test search behavior, null semantics, array membership, and timestamp conversion. Native representations do not authorize unrelated API or domain-model changes.

Remove helpers that emulate searches already supported by the selected Drizzle ORM version, especially serialized-text JSON/array matching. Use Drizzle's native operators directly where available; do not port or rename SQLite workarounds into a new compatibility layer. Keep QueryFilter and QueryMatch as distinct public contracts ([ADR-0002](0002-querymatch-distinct-from-queryfilter.md)); translation of those contracts is separate from emulating database capabilities. For required JSONB operations without a supported Drizzle helper, use narrowly scoped parameterized PostgreSQL expressions rather than serialized-text search, and document the gap. Test intended text-search case sensitivity, wildcard escaping, and structural collection semantics; document intentional behavior changes.

## Database Commands and Upgrade Delivery

Remove the libSQL replica `sync` operation and its scripts rather than repurposing it as schema push. Retain explicit migration, seed, and reset operations under the existing ownership boundaries. Reset only the app-owned schema, require an explicit disposable-environment declaration, and leave Mastra and vector schemas untouched unless a separate operation is explicitly requested.

Ship the AI-agent upgrade prompt as a copyable section of the migration guide, alongside a maintainer checklist. Cover framework and app table inventories, native field mappings, transfer planning, validation, and maintainer-run migration generation. Deliver the migration as one coordinated breaking release, with every publishable package in lockstep ([ADR-0018](0018-one-release-for-publishable-packages.md)); choose the exact release version during release preparation.

## Considered Options

- Retain SQLite/libSQL as a supported runtime or local-development fallback: rejected in favor of one PostgreSQL-only persistence contract.
- Replace only the deployed app's driver: rejected because the removal includes reusable framework contracts and generated apps.
- Preserve Starter's lack of configured durable Mastra Memory: rejected in favor of persistent conversations out of the box, with app-owned composition.

## Implementation Verification Gates

Verify driver/dependency versions, PostgreSQL/pgvector version compatibility, PgBouncer transaction-pooling behavior, Drizzle operator availability, and Mastra adapter naming/initialization capabilities before relying on them. Produce field-level mappings from actual schemas, and report unsupported capabilities instead of silently changing the agreed boundaries. This record captures the agreed design, not a completed implementation or an environment-specific production cutover procedure.
