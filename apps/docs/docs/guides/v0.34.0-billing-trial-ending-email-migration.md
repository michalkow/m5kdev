# Billing trial-ending email in 0.34.0

## Summary

`BillingModule` requires `EmailModule`. On Stripe
`customer.subscription.trial_will_end`, Billing emails a portal CTA when Stripe
would cancel the Trial for a missing payment method. There is no Workflow or
Recurrence clock — Stripe already owns Trial length.

There is **no** `create-m5kdev` registry transform. Template add/merge is the
existing `m5kdev update` reconciler.

## Who needs this migration

- **Every app** that registers `BillingModule` without `EmailModule` — boot
  fails until Email is in the `createBackendApp` modules array. Auth already
  `dependsOn` Email, so apps that boot Auth plus Billing only need to confirm
  Email is registered.
- Apps that want the warning email must register a `trialEnding` template and
  subscribe the Stripe webhook to `customer.subscription.trial_will_end`.
- Apps that keep Billing but skip the email can omit the template; Billing logs
  and returns success.

New apps scaffolded on this release get the Starter `trialEnding` template even
when the `billing` create flag is off (the flag records a feature id and does
not scaffold `BillingModule`).

## Prerequisites and upgrade order

Complete [Core Modules and Optional Backend Module packages](./v0.34.0-core-optional-backend-modules-migration.md)
in the same release when those diffs apply.

1. Commit or stash application changes.
2. Upgrade `@m5kdev/backend` and `create-m5kdev` together (Managed catalog lockstep).
3. Register `EmailModule` before `BillingModule` if it was missing.
4. Add the template and Stripe event if you want the warning.

Always invoke an exact CLI release:

```sh
pnpm dlx create-m5kdev@0.34.0 update --dry-run
```

## What changed

- `BillingModule.dependsOn = ["email"]`. Missing Email throws the existing
  missing-dependency Kernel error at boot.
- `BillingService.processEvent` handles `customer.subscription.trial_will_end`
  after the usual subscription sync.
- Send runs only when all of these hold: a `trialEnding` template is
  registered; `subscription.trial_settings.end_behavior.missing_payment_method`
  is `"cancel"`; neither the Subscription nor the Customer has a default
  payment method; the User has an email. Otherwise Billing skips (including a
  missing template).
- The email uses `sendBrandTemplate` with `{ url, trialEnd }` — `url` is a
  Stripe Billing Portal session, `trialEnd` is an ISO date or omitted.
- Starter ships `trialEndingEmail.tsx`, registers it on `templates.trialEnding`,
  and adds `trialEnding.*` copy in email i18n.

## Dependency and catalog changes

No new third-party dependencies. `@m5kdev/backend` and `create-m5kdev` move
together on the Managed catalog. `trialEnding` is an optional key on
`EmailTemplates` in `@m5kdev/backend` — existing required auth templates are
unchanged.

## Starter and template file changes

| Path | Existing app |
| --- | --- |
| `apps/email/src/emails/trialEndingEmail.tsx` | Add (merge on unmodified starter email packages). |
| `apps/email/src/index.ts` | Register `trialEnding` on the templates object (**Conditional** if customized). |
| `apps/email/src/resources.ts` | Add `trialEnding` subject / preview / title / body / action keys (**Conditional**). |
| `apps/server/src/app.ts` | **Conditional**. Ensure `new EmailModule(templates)` is in the modules array with `BillingModule`. Starter does not register Billing unless you add it. |

## Migration steps

1. **Manual** — Register `EmailModule` in the same `createBackendApp` call as
   `BillingModule` if it is missing:

```ts
import { createBackendApp } from "@m5kdev/backend/app";
import { BillingModule } from "@m5kdev/backend/modules/billing/billing.module";
import { EmailModule } from "@m5kdev/backend/modules/email/email.module";

createBackendApp(config, [
  new EmailModule(templates),
  new BillingModule({ stripe }, { plans, trial }),
]);
```

2. **Automatic** / **Conditional** — `m5kdev update` merges the Starter
   `trialEnding` template into an unmodified email package. If `index.ts` or
   `resources.ts` were customized, copy the template and register it by hand.

3. **Manual** — In the Stripe Dashboard, include
   `customer.subscription.trial_will_end` on the Billing webhook that posts to
   `POST /webhook` (`STRIPE_WEBHOOK_SECRET`). Stripe fires that event about
   three days before Trial end.

4. **Conditional** — No action if you do not want the email. Leave
   `trialEnding` unregistered; Billing will not fail the webhook.

## Database migration

None. Table definitions are unchanged. Do not hand-write SQL.

## Environment and deployment changes

No new required env. `STRIPE_WEBHOOK_SECRET` is still required to verify
Billing webhooks. Portal session creation uses the existing Stripe client.

## Verification

- App boot succeeds with `BillingModule` and `EmailModule` both registered.
- Boot fails with `Backend module "billing" is missing required dependency "email"`
  if Email is omitted.
- With `trialEnding` registered, a `trial_will_end` event for a cancel-on-missing-PM
  Trial and no default payment method stores/sends mail with a portal URL.
- Without the template, the same event syncs the subscription and skips send
  (`Skipping trial-ending email because the template is unregistered`).

In this repo: `packages/backend/src/modules/billing/billing.service.test.ts`.

## Rollback

Pin the previous `@m5kdev/backend` line. `dependsOn email` and the
`trial_will_end` send path go away. Keep the template files; they are unused on
an older Kernel.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Backend module "billing" is missing required dependency "email"` | Billing without Email | Register `EmailModule` |
| Webhook 200 but no email | Template missing, User has no email, a default PM exists, or `missing_payment_method` is not `"cancel"` | Register `trialEnding`; confirm Stripe Trial cancel behavior and payment method |
| Event never arrives | Dashboard endpoint omits `trial_will_end` | Add the event to the Billing webhook |
| Email has no CTA URL | Portal session failed | Check Stripe customer id on the User |
