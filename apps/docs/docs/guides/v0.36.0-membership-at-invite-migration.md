# Membership at invite in 0.36.0

## Summary

Invite used to create only a Better Auth **Invitation**. Apps that stamp
**MemberId** on org-scoped work had nothing to stamp until accept. Auth now
creates a **Membership** at invite (`userId` unset; email and name snapshots).
Accept attaches the User to that same row. Cancel, lazy expiry, leave, and
remove **soft-delete** the Membership; re-invite **revives** `memberId`.

**Invitation** is only the accept token (link, expiry, `memberId`). There is
**no** Invitation backfill. Tokens without `memberId` fail on accept until the
Organization sends a new Auth invite.

Org self-service cannot grant or change **Owner**. Only a User-role `admin`
transfers Owner (or assigns Owner when there is none). Signup still creates the
personal-org Owner.

Capability docs: [Auth](/modules/auth),
[Organizations and members](/guides/organizations-and-members).
Decision records: ADR-0011
(`docs/adr/0011-membership-exists-before-user.md`), ADR-0012
(`docs/adr/0012-one-owner-platform-admin-transfers.md`).

There is **no** `create-m5kdev` registry transform. Schema generation is
**Manual**. Web-ui members UI is in the package bump; forked copies are
**Manual**.

## Who needs this migration

- **Every Auth app** that bumps `@m5kdev/backend` to 0.36.0. Schema and Auth
  tRPC change for all of them.
- **Apps whose members UI still calls Better Auth** `inviteMember`,
  `acceptInvitation`, `cancelInvitation`, `listInvitations`,
  `updateMemberRole`, or `removeMember` (or the unreleased
  `auth.updateInvitationRole` tRPC).
- **Apps with pending invitation emails** sent before this release: those
  accept links fail until a new Auth invite.

No action if the app never registered Auth. New apps scaffolded on this
release already use Auth tRPC and assignable roles without Owner.

Complete [Member ownership in 0.32.0](/guides/v0.32.0-memberid-ownership-migration)
and the [0.35.0 upgrades](/#upgrade-0-35-0) first. On the 0.36.0 bump, also
run [Account claim and Waitlist](/guides/v0.36.0-account-claim-waitlist-migration)
and [Team drop](/guides/v0.36.0-team-drop-migration). Auth schema steps can
share **one** Drizzle generate after the catalog bump.

1. Commit or stash application changes.
2. Upgrade `@m5kdev/commons`, `@m5kdev/backend`, `@m5kdev/frontend`,
   `@m5kdev/web-ui`, and `create-m5kdev` together (Managed catalog lockstep).
3. Generate and apply Drizzle migrations for Auth `members` / `invitations`.
4. Point invite / accept / cancel / list / role / remove / leave at Auth tRPC.
5. Drop Better Auth organization invitation HTTP and `updateInvitationRole`.
6. Strip Owner from org `assignableRoles`. Re-invite any in-flight leftover
   tokens.

Always invoke an exact CLI release:

```sh

```

## What changed

### Membership at invite

- `members.userId` is nullable. Invited seats have `userId` unset.
- `members.email` snapshots the invite email (and later the User email).
- `invitations.memberId` points at that Membership. A pending token without
  `memberId` is a leftover from before this change.
- One live (`deletedAt` null) Membership per email per Organization while
  `userId` is unset. One attached row per UserId plus Organization **including
  soft-deleted rows**, so revive is an update rather than a second insert.
  Unique indexes enforce that in the database.
- Invited Members are not Actors. Platform admin add-member still attaches an
  existing User immediately (no Invitation).

### Auth tRPC (replace Better Auth invitation HTTP)

| Procedure | Auth | Notes |
| --- | --- | --- |
| `inviteOrganizationMember` | organization `write` | `{ email, role }`. Refuses Owner. Resend if live invited seat; revive a left `memberId`; leftover pending tokens for that email are canceled first. |
| `listOrganizationMembers` | organization `read` | Lazy-expires pending tokens (same soft-delete as cancel), then lists live members. Pending rows include `invitationId`. |
| `updateMemberRole` | organization `write` | `{ memberId, role }` for invited and active seats. Copies onto the pending Invitation. Refuses Owner assignment and changing an Owner row. Replaces `updateInvitationRole`. |
| `acceptOrganizationInvitation` | `privateProcedure` (`requireAuth("user")`) | `{ id }`. Attaches User to the existing Membership. Fails without `memberId`, on expiry (after cancel), or email mismatch. |
| `cancelOrganizationInvitation` | organization `write` | `{ invitationId }`. Soft-deletes the invited Membership; token `status: "canceled"`. |
| `removeOrganizationMember` | organization `write` | `{ memberId }`. Soft-delete. Refuses if the target role is Owner. |
| `leaveOrganization` | organization (no `write`) | Soft-deletes `ctx.actor.memberId`. Owner cannot leave. |
| `transferOrganizationOwner` | `adminProcedure` | `{ organizationId, memberId }`. Exactly one live Owner; target must be active (`userId` set). Previous Owner becomes `admin` in the same transaction. |
| `addAdminOrganizationMember` | admin | May assign Owner only when there is no live Owner. |
| `updateAdminOrganizationMemberRole` | admin | Cannot grant Owner (use transfer or add-member repair). May demote extra Owners to `admin`. |

Signup with an organization invite code attaches via `memberId` and **does
not** create a second personal Organization. `createOrganizationWithOwner` still
sets Owner on personal-org signup.

### Leftover tokens (no backfill)

Pending Invitations from before this change are not updated. Accept of a token
with no `memberId` returns `BAD_REQUEST` ("Invitation has no Membership").
The Organization must send a new Auth invite. That invite cancels leftover
pending tokens for the email, then creates a Membership and a new Invitation.

Expired pending tokens are applied lazily on list or accept (same as cancel).
There is no expiry job.

### Owner

- Default organization `assignableRoles` are `["member", "admin"]`.
  `normalizeAuthRolesConfig` strips `owner` from organization assignable roles
  even if an app lists it.
- Extra Owners from before this rule are not auto-demoted. While more than one
  live Owner exists, Auth refuses Owner grants and transfer; Admin demotes
  extras via `updateAdminOrganizationMemberRole`.

### Frontend / web-ui

- `useAuthMemberInvite` calls `auth.inviteOrganizationMember` and invalidates
  `listOrganizationMembers`.
- `AuthOrganizationMembersRoute` is one Member list (active + invited). It
  does **not** call Better Auth `inviteMember`, `acceptInvitation`,
  `cancelInvitation`, `listInvitations`, `updateMemberRole`, or `removeMember`.
- Owner row Role is a label (not a picker); Owner cannot be removed from org
  UI.
- `AuthOrganizationAcceptInvitationRoute` stays on
  `/organization/accept-invitation` in `AuthPublicRouter` and calls
  `acceptOrganizationInvitation`. `authClient.organization.setActive` remains
  Better Auth.
- Admin org management: Transfer Owner when there is exactly one live Owner;
  add-member Owner only when there is none.

## Migration steps

1. **Manual** — Upgrade catalog pins for `@m5kdev/commons`,
   `@m5kdev/backend`, `@m5kdev/frontend`, and `@m5kdev/web-ui` to `0.36.0`.
   `pnpm install`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — may merge
   Starter `assignableRoles` if that path is merge-clean. There is no registry
   `id` `0.36.0-membership-at-invite`.
3. **Manual** — Inspect duplicates **before** generate/apply. The unique
   indexes fail if you already have two attached rows for the same User in
   one Organization (including one soft-deleted), or two live pending rows
   for the same email. Collapse extras so revive can be an update. Then
   generate Drizzle migrations with the project's usual command (do not
   hand-write SQL). Apply them before serving traffic on the new Auth code.
   Expected Auth schema:
   - `members.user_id` nullable (FK to `users` remains)
   - `members.email` text, nullable
   - `invitations.member_id` text, nullable FK to `members`
   - unique index `members_attached_user_organization_unique` on
     (`user_id`, `organization_id`) where `user_id` is not null
   - unique index `members_live_pending_email_organization_unique` on
     (`email`, `organization_id`) where `user_id` is null and `deleted_at`
     is null
4. **Manual** — Replace call sites:

   ```ts
   // invite
   trpc.auth.inviteOrganizationMember.mutate({ email, role });

   // list (one list; invited rows have invitationId, userId null)
   trpc.auth.listOrganizationMembers.query();

   // role (invited or active)
   trpc.auth.updateMemberRole.mutate({ memberId, role });

   // accept (logged-in User; public route still hosts the page)
   trpc.auth.acceptOrganizationInvitation.mutate({ id: invitationId });

   // cancel / remove / leave
   trpc.auth.cancelOrganizationInvitation.mutate({ invitationId });
   trpc.auth.removeOrganizationMember.mutate({ memberId });
   trpc.auth.leaveOrganization.mutate();
   ```

   Delete `updateInvitationRole` usage. Do not call Better Auth
   `organization.inviteMember`, `acceptInvitation`, `cancelInvitation`,
   `listInvitations`, `updateMemberRole`, or `removeMember` for this UI.
5. **Conditional** (forked members UI) — Switch to
   `AuthOrganizationMembersRoute` or the same tRPC. Keep
   `/organization/accept-invitation` on the public router.
6. **Manual** — Set organization `assignableRoles` to exclude `"owner"`.
   `defineAuthRoles` strips it if you forget.
7. **Manual** — Re-invite anyone with an outstanding pre-migration accept
   link. Tell them the old email will not work.
8. **Conditional** (multiple live Owners) — In Auth admin org members, demote
   extras to `admin`, then use Transfer Owner. Do not expect an automatic
   demotion.

## Database migration

Schema change. **Do not** create Drizzle migration files by hand. Run the
project's migration generation command, review the SQL, then apply.

There is **no data backfill** of `invitations.member_id`. Existing pending
rows stay as leftover tokens until canceled by a new Auth invite or by
lazy expiry/cancel.

Soft-deleted memberships from 0.32.0 are unchanged. Invited seats are new
rows with `userId` null, not placeholder Users.

If unique-index creation fails, two seats already exist for the same person.
Do not drop the indexes. Deduplicate (keep the row whose `memberId` is
stamped on org-scoped work), then re-apply.

## Environment and deployment changes

No new required env. Invite email still needs `app.urls.web` (accept URL is
`{web}/organization/accept-invitation?id=`).

- **Rollout order** — apply the Drizzle migration, then deploy backend, then
  web. Accept against new code on old schema cannot write `memberId`.
- **In-flight emails** — old accept links fail after the backend deploy.
  Re-invite; do not write a one-off SQL backfill unless you accept owning it
  (the framework does not).
- **Workers** — none. Expiry is lazy on list/accept.

## Verification

In this repo:

```sh
pnpm --filter @m5kdev/backend test -- src/modules/auth/tests/auth.invitation.test.ts
pnpm --filter @m5kdev/backend test -- src/modules/auth/tests/auth.owner.test.ts
```

In the app:

- Invite a new email: `members` has `userId` null, `email` set, and a pending
  `invitations.member_id`. The members table shows one invited row (not a
  separate invitations page).
- Accept while logged in as that email: same `members.id`, `userId` set.
  Signup with the invite query does not create a second personal Organization.
- Accept a leftover token with no `memberId`: error until you re-invite.
- Cancel / expiry / leave: `deletedAt` set; re-invite reuses `memberId`.
- Org UI cannot pick Owner; Owner row is frozen. Admin transfer with exactly
  one Owner demotes the previous Owner to `admin`.
- `pnpm check-types` / `pnpm lint` succeed after the tRPC cutover.

## Rollback

Revert the `@m5kdev/*` / `create-m5kdev` bump and restore previous members UI
from git. Schema that already made `user_id` nullable can stay; old Better
Auth invite HTTP expected a User on the member row after accept, not at
invite.

Do **not** drop `invitations.member_id` if new invites already wrote it.
Forward-fix leftover tokens by re-invite rather than restoring old accept
behavior.

## Troubleshooting

- **Accept: "Invitation has no Membership"** — leftover token. Send a new
  Auth invite for that email.
- **Accept: "Invitation has expired"** — lazy cancel already ran. Re-invite.
- **Accept: "Invitation email does not match"** — logged-in User email is not
  the invite email.
- **Invite: "A live Membership already exists for this email"** — that email
  is already an active Member (`userId` set).
- **Invite: "Cannot invite the Owner role"** — use Admin transfer / repair.
- **Members list missing invited rows** — still listing Better Auth
  invitations, or listing members without the Auth `listOrganizationMembers`
  join (`invitationId`).
- **Signup created a second Organization** — invite code was missing
  (`organization-invitation-code` / signup query). Auth skips personal-org
  create only when the invite attaches.
- **Several Owners; transfer refused** — demote extras to `admin` in Auth
  admin, then transfer.
- **Unique index fails on migrate** — two attached seats for the same User in
  one Organization, or two live pending rows for the same email. Deduplicate
  first; keep the `memberId` already stamped on org-scoped rows.
- **Type error on `updateInvitationRole`** — procedure is gone; use
  `updateMemberRole({ memberId, role })`.
