# Deployment environments migration

## Summary

An m5kdev app now runs in named **Deployment environments**: Development and
Production always, and Staging and Canary optionally. The Kernel reads the
environment from `APP_ENV` (never `NODE_ENV`, which is `production` on every
deployed app) and the app identity from `APP_SLUG`. It refuses to boot without
them. Both values decide how environments share one Redis safely:

- Workflow queues use the BullMQ prefix `<APP_SLUG>-<APP_ENV>`.
- Server event channels use `<APP_SLUG>:<database scope>:server-event:`.
- Workflow rows record their environment.

Each environment follows a Git branch (`main` → Development, `production` →
Production). A merged pull request migrates that environment's database in
GitHub Actions, then deploys a build of that branch to its own Fly app
(ADR-0035, ADR-0036, ADR-0037).

## Who needs this migration

- **Every app that uses `@m5kdev/backend` (`createBackendApp` or `runDb`).**
  The Kernel throws at boot without `APP_ENV`/`APP_SLUG`. This includes tests,
  e2e servers, and scripts that pass an explicit `env` to `createBackendApp`.
- **Apps with the `workflows` feature (Workflow module).** You need a
  database migration, a Redis queue cutover, and, outside Production, a
  backfill.
- **Apps that deploy with the scaffolded `.github/workflows/deploy-app.yml`.**
  Pushes to `main` now deploy **Development**, not Production. Production
  deploys from the `production` branch.
- **Landing-only apps** (no Kernel): no Kernel changes apply. Landing deploys
  are unchanged (`landing:deploy` / `landing:secrets`). `--environments` is
  refused for Landing-only apps.
- **Code that builds `createServerEventBus` directly** must pass `channelPrefix`.

## Prerequisites and upgrade order

1. Complete all earlier migration guides, including the PostgreSQL migration
   ([PostgreSQL and pgvector migration](./v0.42.0-postgresql-pgvector-migration.md)). This guide assumes PostgreSQL,
   `DATABASE_URL` (PgBouncer) and `DATABASE_DIRECT_URL`.
2. Commit or stash local work: `create-m5kdev update` in write mode needs a
   clean Git worktree.
3. Recommended rollout order:
   1. Upgrade packages and run `create-m5kdev update` on a branch.
   2. Set `APP_ENV`/`APP_SLUG` everywhere (local `.env`, Fly secrets, GitHub
      environment `APP_ENV_FILE`).
   3. Generate and review the Workflow migration (if you have Workflows).
   4. Drain old BullMQ queues, or keep the old prefix for one release (see
      [Environment and deployment changes](#environment-and-deployment-changes)).
   5. Create the GitHub environments, secrets, and the `production` branch.
   6. Merge to `main` (deploys Development), then open a Promotion PR
      `main` → `production`.

## What changed

### Kernel (`@m5kdev/backend`)

| Area | Before | After |
| --- | --- | --- |
| Boot configuration | `NODE_ENV` chose behaviour | `APP_ENV` (`local` \| `development` \| `staging` \| `canary` \| `production`) and `APP_SLUG` (lowercase slug) are required; `createBackendApp` throws when either is missing or invalid. Outside `local`, `VITE_APP_URL`/`VITE_SERVER_URL` (or `app.urls.web`/`app.urls.api`) are required too. |
| New helpers | — | `@m5kdev/backend/base/environment`: `parseAppEnvironment`, `isDeployedEnvironment`, `requireEnvValue(name, { localDefault })`, `databaseScope(environment)`, `DEPLOYMENT_ENVIRONMENTS`, type `DeploymentEnvironment`. `appConfig.environment` and `appConfig.slug` are on every module hook context. |
| Email default mode | `send` when `NODE_ENV=production` | `send` when `APP_ENV` is a deployed environment; **`log` when `APP_ENV` is `local` or unset**, even with `NODE_ENV=production`. Set `email.mode` explicitly to override. |
| File module object store | S3 when `NODE_ENV=production` | S3 whenever `APP_ENV` is not `local`; the local object store and its mock S3 router only when `APP_ENV=local`. Staging and Development now need real S3 configuration. |
| Email preview (`EmailPreviewModule`) | Hidden when `NODE_ENV=production` | Mounted only when `APP_ENV=local` (and mode is `store`). |
| MCP e2e CIMD (`M5K_MCP_E2E_CIMD=1`) | Off when `NODE_ENV=production` | Off whenever `APP_ENV` is a deployed environment. |
| Logger | Pretty unless `NODE_ENV=production` | Raw JSON whenever `APP_ENV` is set and not `local`; pretty locally or when unset. |
| Telemetry | `initTelemetry({ env })` defaulted to `NODE_ENV`; console spans unless `production` | Defaults to `APP_ENV`; console span export only when `local` or unset. |
| Workflow queues | BullMQ default prefix `bull` | Prefix `<APP_SLUG>-<APP_ENV>` (the **Environment namespace**). `WorkflowServiceConfig.prefix` is required; `WorkflowModule` sets it and accepts a `prefix` override for a migration. |
| Workflow schedulers | Always registered | `schedulers` option (default: on only where the environment owns its database, `databaseScope(APP_ENV) === APP_ENV`). Canary therefore registers no job schedulers, including the reconcile sweep. Workers start either way. |
| Workflow rows | One row per `job_id` | New `environment` column, unique `(environment, queue_name, job_id)`. Reads, lists, lifecycle updates and reconcile only touch the current environment's rows. `WorkflowRepository` requires `environment`; `touch(jobId, queueName)`. |
| Server events | Redis channels `m5kdev:server-event:<userId>` | `<APP_SLUG>:<scope>:server-event:<userId>`, scope = `databaseScope(APP_ENV)` (Canary shares Production's). Override with `createBackendApp({ serverEvents: { scope } })`. `createServerEventBus({ redis, logger, channelPrefix })` requires `channelPrefix` (use `serverEventChannelPrefix({ slug, scope })`). |
| Health check | — | `GET /healthz` returns `200 { status: "ok", environment }` when PostgreSQL answers, `503` otherwise. No auth. |
| `runDb` `migrate` | No lock | Holds a PostgreSQL advisory lock per migrations schema (concurrent runners wait), sets `lock_timeout` (default `5s`) and `statement_timeout` (default `5min`), and logs `Migrating host:port/db (schema) for APP_ENV=<env>: N pending` plus tags, never credentials. New `RunDbConfig` options: `migrationsSchema` (default `drizzle`), `lockTimeout`, `statementTimeout`, `log`. |
| `runDb` `rebuild` | — | New disposable-only command: drops the app schema and Drizzle's history table, then re-applies every migration. Refuses when another schema has foreign keys into the app schema. Requires `DATABASE_DISPOSABLE=true`. |
| New bin | — | `m5kdev-migration-check --folder <dir> [--base <ref>]`: fails on uncommitted `drizzle:generate` output and, with `--base`, on edited/deleted merged migrations or rewritten journal entries. |

## Migration steps

No entry in `packages/cli/src/migrations/registry.ts`: the automatic steps run
in `m5kdev update`'s reconcile and file-planning phases, not as a semantic
transform.

1. **Manual. Bump packages.** Set the `@m5kdev/*` pins in `pnpm-workspace.yaml`
   to `0.44.0` and run `pnpm install`.
2. **Automatic. Run the updater.**
   ```bash
   pnpm dlx create-m5kdev@0.44.0 update --dry-run
   pnpm dlx create-m5kdev@0.44.0 update
   ```
   Add `--environments staging,canary` (or one of them) to add optional
   environments now. Resolve any conflicts it reports.
3. **Manual. Local env.** In `apps/shared/.env` add:
   ```dotenv
   APP_ENV=local
   APP_SLUG=<app-slug>
   ```
   `APP_SLUG` must match `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` and be the same in every
   environment of the app.
4. **Manual. Server composition** (`apps/server/src/app.ts`):
   ```ts
   import { isDeployedEnvironment, requireEnvValue } from "@m5kdev/backend/base/environment";

   // Local fallbacks apply only when APP_ENV=local; deployed environments fail at boot.
   const appUrl = requireEnvValue("VITE_APP_URL", { localDefault: "http://localhost:5173" });
   const serverUrl = requireEnvValue("VITE_SERVER_URL", { localDefault: "http://localhost:8080" });
   const redisUrl = requireEnvValue("REDIS_URL", { localDefault: "redis://127.0.0.1:6379" });
   // …
   secret: requireEnvValue("BETTER_AUTH_SECRET", { localDefault: "<local-only secret>" }),
   // …
   new EmailPreviewModule({ allowDelete: !isDeployedEnvironment() }),
   ```
   Do **not** set `schedulers` on `WorkflowModule`; the Kernel turns them off
   in Canary. Replace any remaining `process.env.NODE_ENV === "production"`
   checks in your own code with `isDeployedEnvironment()` or
   `appConfig.environment`.
5. **Conditional. Tests and scripts.** Any `createBackendApp({ env: … })` call
   must include `APP_ENV` and `APP_SLUG` (tests usually use `local`). Callers of
   `createServerEventBus` must pass `channelPrefix`. Code that constructs
   `WorkflowRepository` or `WorkflowService` directly must pass `environment`
   and `prefix`.
6. **Conditional (Workflows). Database migration.** See
   [Database migration](#database-migration).
7. **Conditional (Workflows). Queue cutover.** See
   [BullMQ prefix](#bullmq-prefix-workflows).
8. **Manual. Deploy home.** Fill `.env.production` and `.env.development`
   (each with its own `APP_ENV`), check `fly.production.toml` still names your
   existing Production Fly app, then create the Development Fly app:
   `fly apps create <app-slug>-development`.
9. **Manual. GitHub.** See
   [Environment and deployment changes](#environment-and-deployment-changes).
10. **Manual. Cleanup.** After Production deploys from `fly.production.toml`,
    delete `apps/shared/fly.toml` and the old repository secrets
    `FLY_API_TOKEN_APP` and `APP_ENV_PRODUCTION`.

## Database migration

**Conditional: apps with the Workflow module.** The Kernel table `workflows`
gains:

- `environment text NOT NULL DEFAULT 'production'`
- unique constraint `workflows_environment_queue_job_unique` on
  `(environment, queue_name, job_id)`

The old unique on `job_id` stays for one release, so the previous release's
`ON CONFLICT (job_id)` keeps working while both versions run. A later release
drops it ([michalkow/m5kdev#59](https://github.com/michalkow/m5kdev/issues/59)).

Never write the migration by hand. Run the project's generator and review the
SQL:

```bash
pnpm --filter ./apps/server drizzle:generate
```

Expected SQL (schema name follows `DATABASE_SCHEMA`):

```sql
ALTER TABLE "app"."workflows" ADD COLUMN "environment" text DEFAULT 'production' NOT NULL;
ALTER TABLE "app"."workflows" ADD CONSTRAINT "workflows_environment_queue_job_unique" UNIQUE("environment","queue_name","job_id");
```

Commit the generated files. The deploy workflow applies them (`migrate` job)
before each environment deploys. Never edit a migration after it merges; the
CI frozen-history check fails if you do.

**Backfill for non-production databases.** The default `'production'` is the
backward-compatible value for existing rows, not a namespace. In a database
that belongs to another environment (Development, Staging, or a local
database), existing rows would be invisible to that environment's reads and
reconcile. After the migration, run once per database:

```sql
-- Development database
UPDATE "app"."workflows" SET environment = 'development' WHERE environment = 'production';
-- Staging database
UPDATE "app"."workflows" SET environment = 'staging' WHERE environment = 'production';
-- Local database
UPDATE "app"."workflows" SET environment = 'local' WHERE environment = 'production';
```

Skipping it is harmless but leaves old non-terminal rows `queued`/`running`
forever. The Production database (also used by Canary) needs no backfill.

**Canary and deterministic job ids.** Until [#59](https://github.com/michalkow/m5kdev/issues/59) ships, a deterministic job id
(`id` on a Workflow job) that Production already used cannot also be recorded
by Canary: the job runs, but its row write fails and is logged. Avoid
triggering deterministic-id jobs on Canary until then.

## Environment and deployment changes

### Required variables

| Variable | Where | Value |
| --- | --- | --- |
| `APP_ENV` | every `.env*` file, Fly secrets (through `app:secrets:<env>`), each GitHub environment's `APP_ENV_FILE` | `local`, `development`, `staging`, `canary`, or `production` |
| `APP_SLUG` | same | the app's slug, identical everywhere |
| `VITE_APP_URL`, `VITE_SERVER_URL` | every deployed environment | that environment's public URLs (boot fails without them) |
| `DATABASE_DIRECT_URL` | GitHub environment secret | that environment's direct (non-pooled) URL; Canary uses Production's |

### BullMQ prefix (Workflows)

Queues move from `bull:<queue>:*` to `<APP_SLUG>-<APP_ENV>:<queue>:*`. The new
release does not see jobs or job schedulers under `bull:`. Choose one:

- **Drain first (recommended).** Stop producers, wait until every queue is
  empty (Bull Board at `/admin/queues`, or `getJobCounts`), then deploy.
- **Keep the old prefix for one release.** Set `prefix: "bull"` on
  `WorkflowModule` in Production only, deploy, drain, then remove the override
  and deploy again. Never ship `prefix: "bull"` to two environments sharing a
  Redis.

After switching, remove the old job schedulers under `bull:` (Bull Board or
`redis-cli --scan --pattern 'bull:*'`). Otherwise they keep adding jobs no
worker reads.

### Server events

Channels move from `m5kdev:server-event:` to
`<APP_SLUG>:<scope>:server-event:`. During the upgrade deploy, old and new
machines listen on different channels, so **Server events emitted while both
versions run may be dropped** ([michalkow/m5kdev#51](https://github.com/michalkow/m5kdev/issues/51)). No data is lost, but a
live view may stay stale until its queries refetch. When the deploy restarts a
browser's stream, `ServerEventProvider`'s `onReconnect` handler runs if your app
sets one (for example to invalidate queries).

### Deploy workflow and GitHub setup

1. Create GitHub environments **`development`** and **`production`** (and
   `staging`/`canary` if enabled), Settings → Environments. Add to each:
   - `FLY_API_TOKEN`: `fly tokens create deploy --app <fly app>`
   - `APP_ENV_FILE`: the full contents of that environment's
     `apps/shared/.env.<environment>`
   - `DATABASE_DIRECT_URL`: that database's direct URL (only the migrate step
     sees it)
2. Move the old repository secrets: `FLY_API_TOKEN_APP` → `production` /
   `FLY_API_TOKEN`, `APP_ENV_PRODUCTION` → `production` / `APP_ENV_FILE`.
3. Create the `production` branch from the commit Production runs today, and
   protect it: no direct pushes, require the **Promotion PR** check. Restrict
   the `production` environment to the `production` branch.
4. Merge Promotion PRs with a **merge commit** (no squash or rebase). The
   `resolve` job fails, before migrating, when a release branch's tree does not
   match a commit on its source branch.
5. **Behaviour change:** a push to `main` now deploys **Development**. Production
   deploys only after a Promotion PR `main` → `production` merges.
6. Migrations now run in GitHub Actions on every deploy (`migrate` job, then
   `deploy`). Do not add a Fly `release_command`. A migration that waits more
   than 5 s for a table lock now fails instead of blocking traffic: raise
   `lockTimeout` in your `runDb` config for a known-long operation, or schedule
   it.

### Optional environments

- **Staging:** its own database (a Neon branch derived from Production) and Fly
  app `<app-slug>-staging`. Schedulers run, so test recurring jobs here.
- **Canary:** Production's database URLs with `APP_ENV=canary`. Its deploy
  migrates the Production database. Its workers write real Production data;
  schedulers stay off; it shares Server events with Production. Use test
  accounts. Protect the `canary` environment with required reviewers.
- Add later with `create-m5kdev update --environments canary` (or `staging`).
  The chain is `main` → [`staging`] → [`canary`] → `production`.

Full instructions: [Deployment environments](./deployment-environments.md).

pnpm --filter ./apps/server drizzle:generate   # expect: "No schema changes, nothing to migrate"

Expected results:

- `pnpm dev` boots locally. Removing `APP_ENV` from `.env` makes boot fail with
  `APP_ENV must be one of local, development, staging, canary, production`.
- `curl http://localhost:8080/healthz` returns
  `{"status":"ok","environment":"local"}`.
- Locally, email defaults to `log` and the email preview is available in
  `store` mode.
- `pnpm --filter ./apps/server exec tsx db.ts migrate` logs
  `Migrating <host:port/db> (drizzle) for APP_ENV=local: 0 pending`.
- `pnpm app:deploy` prints `Use pnpm app:deploy:<environment> — one of: development, production` and exits 1.
- With Workflows: new Redis keys use `<app-slug>-local:` locally and
  `<app-slug>-production:` in Production. Canary's logs show workers starting
  and no job schedulers registered.
- After merging to `main`: the Deploy app run shows `resolve` → `migrate` →
  `deploy` for `development`, and the Development Fly app answers `/healthz`
  with `"environment":"development"`.

## Rollback

- **Application code, workflows, and Fly configs** can be reverted with Git and
  redeployed. Keep `fly.toml` until the new Production deploy succeeds, so the
  old workflow can still deploy it.
- **Workflow migration:** additive and backward-compatible (the `job_id` unique
  stays), so the previous release runs against the migrated schema. Do not drop
  the column to roll back; revert code only. If you must undo it, write a new
  forward migration through `drizzle:generate`. Never edit or delete the merged
  one.
- **Backfill:** `UPDATE … SET environment = 'production' WHERE environment = '<env>'`
  restores the pre-backfill value.
- **Queues:** the old release reads only `bull:`, so jobs enqueued under
  `<app-slug>-<env>:` are invisible to it. Drain them before rolling back.
- **Server events:** rolling back changes channels again; events in flight
  during that deploy may be dropped, as on the upgrade.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `APP_ENV must be one of …` at boot | `APP_ENV` missing or misspelled (for example `prod`) | Set it in `.env`/`.env.<env>` and re-run `app:secrets:<env>`. |
| `APP_SLUG must be a lowercase slug …` | Missing or uppercase slug | Use the app slug, for example `editorial-desk`. |
| `VITE_APP_URL (or app.urls.web) must be set when APP_ENV=…` | Deployed environment without public URLs | Add both URLs to that environment's env file. |
| `<NAME> must be set when APP_ENV=…` | `requireEnvValue` found no value outside `local` | Set the variable in that environment. |
| Jobs stuck after deploy, Bull Board empty | Jobs still under the old `bull:` prefix | Drain with `prefix: "bull"` for one release. |
| Recurring jobs never run on Canary | Intended: Canary has no schedulers | Test crons on Staging or Production. |
| Old Workflow rows stuck `queued` in Development | No backfill | Run the backfill SQL for that database. |
| Canary logs a unique violation on `workflows_job_id_unique` | Deterministic job id already used by Production | Avoid deterministic-id jobs on Canary until #59. |
| Deploy fails in `resolve`: "does not match any commit on main" | Commit pushed directly to `production`, or a squash/rebase Promotion merge | Re-promote with a merge-commit Promotion PR from `main`. |
| Deploy fails: "Configure DATABASE_DIRECT_URL in this GitHub environment." | Missing environment secret | Add it to that GitHub environment. |
| Migrate fails with `lock timeout` | A long transaction holds the table | Retry off-peak, or raise `lockTimeout` for that run. |
| Staging uploads fail | File module now uses S3 outside `local` | Configure the `AWS_*` variables for that environment. |
| No emails sent from a local `NODE_ENV=production` run | Email default follows `APP_ENV` | Set `email.mode: "send"` explicitly or use a deployed `APP_ENV`. |
