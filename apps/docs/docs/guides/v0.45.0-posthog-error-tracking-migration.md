# PostHog error tracking migration

## Summary

PostHog replaces Sentry for backend error reporting and captures browser/React failures. Error capture stays optional,
reports unexpected server failures once, and preserves native causes, structured
context, available User/Organization identity, and OpenTelemetry trace identifiers.

The Webapp bundles the PostHog exception extension, explicitly enables uncaught
errors and unhandled rejections, and reports React render failures with component
context. Its translated recovery screen offers **Reload page**. Expected tRPC
mutation errors are not indiscriminately recaptured in the browser.

## Who needs this migration

Apps using `@m5kdev/backend` error reporting or the Starter server instrumentation.
Apps with custom Sentry reporter adapters, imports, or log consumers must migrate
those contracts. Expo/native instrumentation is outside this migration.

## Prerequisites and upgrade order

Use Node.js 24 and upgrade `@m5kdev/backend` and `create-m5kdev` to **0.45.0** with
the rest of the lockstep m5kdev release. First update the Managed catalog, then
server composition, custom reporting integrations, and deployment configuration.
Configure a PostHog project before enabling capture.

## What changed

- `initPosthog` and `shutdownPosthog` explicitly initialize and flush one optional
  client shared by error reporting and existing analytics helpers.
- `ErrorReporter.captureException(error, properties)` accepts flat structured
  properties. Sentry's hint/`extra` types are removed.
- `ServerError.sentryEventId` becomes `errorEventId`, including serialized errors
  and structured boundary logs. The ID matches the PostHog event UUID.
- `lib/sentry` and its `@sentry/node` dependency are removed; the old eager
  `posthogClient` export is replaced by explicit initialization.
- Expected 4xx failures remain local logs. ServerError capture remains idempotent;
  terminal plain Workflow failures capture once, and intermediate retries warn.
  Errors already captured when created retain that capture on retries.
- Errors still annotate active OTel spans when PostHog is unconfigured.

## Dependency and catalog changes

The Managed catalog removes `@sentry/node` and upgrades `posthog-node` from
`4.10.2` to **5.68.2**. Remove an app's direct Sentry dependency if no other
integration needs it. Refresh the pnpm lockfile after catalog/package updates.
The generated-app catalog is rendered from the root catalog during CLI template
preparation; do not retain a private second SDK pin.

register a no-op migration.

## Migration steps

1. **Manual:** update the catalog/dependencies above and run `pnpm install`.
2. **Manual:** initialize OTel before loading PostHog/reporting modules. The
   CommonJS Starter instrumentation uses a deferred require after `initTelemetry`:

   ```ts
   const { initPosthog } =
     require("@m5kdev/backend/lib/posthog") as typeof import("@m5kdev/backend/lib/posthog");
   initPosthog();
   ```

   An ESM app can import its OTel instrumentation first, then a separate PostHog
   instrumentation module that imports and invokes `initPosthog`. Do not import
   the reporter before the OTel initialization runs.
3. **Manual:** compose shutdown through the existing Kernel hook:

   ```ts
   import { shutdownPosthog } from "@m5kdev/backend/lib/posthog";
   import { shutdownTelemetry } from "@m5kdev/backend/lib/otel";

   // Within createBackendApp configuration:
   onShutdown: async () => {
     await Promise.all([shutdownPosthog(), shutdownTelemetry()]);
   },
   ```

4. **Conditional:** replace `sentryEventId` reads with `errorEventId` and Sentry
   hints with flat `ErrorProperties`. Custom `setErrorReporter` adapters accept
   `(error, properties)` and return a correlation ID or `undefined`.
5. **Conditional:** remove `lib/sentry`, eager `posthogClient` imports, Sentry
   initialization, and obsolete Sentry secrets from your application's setup.
   Existing analytics helpers use the client registered by `initPosthog`.

6. **Conditional (Webapp):** copy the browser initializer and error boundary into
   the equivalent app paths. Pass the optional client from `main.tsx` through
   `App` into `Providers`. Keep the existing route tree and centralize the
   PostHog provider and global providers in `Providers.tsx`. Retain i18next error
   messages and the help-page recovery instructions.

## Database migration

None. The diff changes no tables, migrations, snapshots, or stored records.

## Environment and deployment changes

Set `VITE_PUBLIC_POSTHOG_KEY` to the public project ingestion token and
`VITE_PUBLIC_POSTHOG_HOST` to its ingestion host, for example
`https://us.i.posthog.com` or `https://eu.i.posthog.com`. The server and browser
share these public configuration values. Missing, empty, or `demo` keys disable
initialization. OTel configuration remains independent.

## Verification

Run `pnpm install`, package builds, affected type checks, lint, and focused tests.
In this monorepo:

```sh
pnpm --filter @m5kdev/commons build
pnpm --filter @m5kdev/backend test --runInBand src/utils/errors.test.ts src/lib/posthog.test.ts src/modules/workflow/tests/workflow.registry.test.ts
pnpm --filter @m5kdev/backend check-types
pnpm --filter @m5kdev/backend build
pnpm --filter @starter-app/server check-types
pnpm --filter @starter-app/webapp test --runInBand
pnpm --filter @starter-app/webapp check-types
pnpm --filter @starter-app/webapp build
pnpm --filter @starter-app/docs build
pnpm --filter create-m5kdev prepare:templates
pnpm --filter create-m5kdev test
pnpm docs:build
```

With a real configured project, provoke one deliberate backend 5xx and one failed
Workflow. Confirm exception cause/context and available identity in PostHog,
match `errorEventId` in logs, and verify the existing OTel error span. A 4xx should
produce a local warning without an exception event. Restart/shutdown must flush
pending events. Automated tests use an external network stub, not live credentials.

## Rollback

Revert application wiring, catalog, lockfile, and log-field queries together to
the previous release. Restore your previous Sentry integration if needed. There
is no database rollback or historical-event import. Disable PostHog by clearing
its public project token if you need to stop capture independently of OTel.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| No backend exceptions | Ensure `initPosthog` runs and the ingestion token is neither empty nor `demo` |
| Logs use a missing Sentry ID | Update consumers to `errorEventId` |
| Missing identity | Ensure the request or job supplies User/Organization identifiers; anonymous failures remain reportable |
| Missing OTel correlation | Load OTel before error/logger modules and verify existing OTLP configuration |
| Lost buffered events on stop | Await `shutdownPosthog` in Kernel `onShutdown` |
