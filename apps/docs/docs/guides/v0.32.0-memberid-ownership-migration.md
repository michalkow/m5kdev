# Member ownership migration in 0.32.0

:::note Open question
Confirm the published release number before linking this guide from release
notes. Packages in the monorepo may still report `0.31.x` until the release is
cut; rename the file and `migration.id` / `target_version` if the ship version
differs from `0.32.0`.
:::

## Summary

m5kdev treats **organizations as the default tenancy model**. Org-scoped assets
must key ownership and `"own"` grants on **`memberId`** (the `members` row), not
only on `userId`. Memberships soft-delete on leave/remove and revive on rejoin
so historical attribution and the same `memberId` survive.

This release updates:

- `members` with snapshot `name`, `image`, and `deletedAt`
- Grant / context-filter behavior for org-scoped `"own"`
- First-party asset tables (`files`, `tags`, `recurrence`) with nullable
  `member_id`
- Auth actor requirements (`memberId` for org/team scopes)
- Starter `posts.member_id` as the app-module pattern

Personal resources (billing, devices, OAuth) stay on `userId`.

Conceptual background:
[Organizations and members](/guides/organizations-and-members).

## Who needs this migration

- **Every existing app** on `@m5kdev/backend` / `@m5kdev/frontend` before this
  release that stores org-scoped rows keyed only by `userId`.
- Apps with custom modules that authorize `"own"` via `userId` inside an
  organization context.
- Apps that hard-delete `members` rows and need durable attribution.

No action is required only if the app has **no database** and **no custom
org-scoped tables** (unlikely for a production m5kdev app).

## Prerequisites and upgrade order

1. Finish any earlier auth/locale/roles migrations your app still needs
   ([custom app roles](/guides/custom-app-roles-migration),
   [user/org locale](/guides/user-org-locale-migration)).
2. Upgrade all `@m5kdev/*` packages together to the `0.32.0` line (do not mix
   with older `@m5kdev/backend`).
3. Generate and apply **schema** migrations for framework + app tables.
4. Run **data backfills** for `members.name` and asset `member_id` columns.
5. Cut over app services to stamp and authorize with `memberId`.
6. Smoke-test leave/rejoin and `"own"` access in an organization session.

There is **no** `create-m5kdev` registry transform for this migration. Every
application step is **Manual**.

## What changed

### Members

| Column | Change |
| --- | --- |
| `members.name` | Not-null snapshot of the user’s display name (default `""`). Synced while membership is active; retained after soft-delete. |
| `members.image` | Nullable snapshot of the user’s image / OAuth avatar. Copied on signup and member create/revive; synced while membership is active; retained after soft-delete. |
| `members.deletedAt` | Soft-delete marker. Active membership requires `NULL`. |

Remove / leave soft-deletes instead of hard-deleting. Rejoin or invite accept
for the same `(userId, organizationId)` **revives** the row (same `memberId`).

Better Auth’s member adapter is wrapped so delete/create/find/list honor
soft-delete and revive.

### Grants and actors

- `Entity` accepts `memberId`.
- In organization context, user-level `"own"` prefers `memberId`.
- Legacy dual-read: org rows without `memberId` still compare `userId`.
- `ownership: "member"` means member-owned via `memberId`, not the role name.
- Org and team actor scopes require `memberId`.
- `addContextFilter` accepts `"member"` for member-owned list scoping.

### First-party modules

Nullable `member_id` (FK → `members.id`, `onDelete: "set null"`) on:

- `files`
- `tags`
- `recurrence`

Services dual-write `userId` + `memberId` and authorize with `memberId` in org
context. Auth member preferences / metadata / onboarding / flags authorize with
`memberId: state.member.id`.

### Frontend

Auth client session additional fields include `activeOrganizationMemberId`
(already used by the server session; ensure the client schema exposes it).

### Starter

`posts` gains `member_id`; create stamps `ctx.actor.memberId` (mapped from
session `activeOrganizationMemberId`). Prefer the column name `memberId` over
role-specific aliases such as `authorMemberId`.

## Migration steps

### 1. Upgrade packages — Manual

Align `@m5kdev/*` to `0.32.0`, reinstall, and fix type errors from actor /
grants / session typing.

### 2. Extend app schema for custom org assets — Manual / Conditional

For each org-scoped table that only has `user_id`, add a nullable membership FK:

```ts
memberId: text("member_id").references(() => members.id, {
  onDelete: "set null",
}),
```

Keep `userId` during dual-write. Do **not** invent migration SQL by hand —
run your project’s Drizzle migration generation command after schema edits
(framework tables + app tables).

### 3. Cut over services — Manual

On create / update stamps:

```ts
userId: ctx.actor.userId,
memberId: ctx.actor.memberId,
organizationId: ctx.actor.organizationId,
```

On `.access({ ... entities })` for `"own"` resources, pass `memberId` (and keep
`userId` for legacy dual-read until backfill completes).

Prefer:

```ts
.requireAuth("organization")
.addContextFilter(["member", "organization"])
```

for lists of “my” org assets.

### 4. Auth client — Manual / Conditional

If the app defines its own Better Auth client fields, include:

```ts
activeOrganizationMemberId: {
  type: "string",
  required: false,
},
```

### 5. Backfill data — Manual

After schema migrate, run backfills (see [Database migration](#database-migration)).

### 6. Cleanup (optional, later) — Conditional

Once every org-scoped row has `member_id` and dual-read is unused in production,
you may stop authorizing solely on `userId` for those tables. Leaving `memberId`
nullable remains valid where `organizationId` itself is optional.

## Database migration

**Do not create Drizzle migration files manually.** After pulling framework
schema changes and editing app tables:

1. Run your app’s usual migration generation command (for example the starter’s
   Drizzle generate script).
2. Review the generated SQL.
3. Apply it in the normal migrate path for each environment.

Expected framework schema effects (SQLite/libSQL naming):

| Table | Columns |
| --- | --- |
| `members` | `name` text not null default `''`; `image` text nullable; `deleted_at` integer nullable |
| `files` | `member_id` text nullable FK → `members.id` |
| `tags` | `member_id` text nullable FK → `members.id` |
| `recurrence` | `member_id` text nullable FK → `members.id` |
| App tables (e.g. `posts`) | e.g. `member_id` text nullable FK → `members.id` |

### Data backfill (run after migrate)

Backfill membership display names and images from users:

```sql
UPDATE members
SET
  name = COALESCE(
    (SELECT users.name FROM users WHERE users.id = members.user_id),
    ''
  ),
  image = COALESCE(
    members.image,
    (SELECT users.image FROM users WHERE users.id = members.user_id)
  )
WHERE name = '' OR name IS NULL OR image IS NULL;
```

Backfill asset `member_id` from the active membership matching the row’s user
and organization (adjust table/column names per app):

```sql
UPDATE files
SET member_id = (
  SELECT members.id
  FROM members
  WHERE members.user_id = files.user_id
    AND members.organization_id = files.organization_id
    AND members.deleted_at IS NULL
  LIMIT 1
)
WHERE files.member_id IS NULL
  AND files.organization_id IS NOT NULL;
```

Repeat for `tags`, `recurrence`, and custom tables (`posts.member_id`
from `author_user_id` + `organization_id`).

Rows without an organization, or without a matching member, stay `NULL` and
continue to use legacy `userId` ownership until fixed.

## Environment and deployment changes

None required for env vars.

Rollout order:

1. Deploy schema migrate + backfill **before** or **with** code that requires
   `memberId` on org-scoped actors.
2. Ensure workers and API instances upgrade together so soft-delete member
   semantics are consistent.
3. Prefer running backfills in a maintenance window for large `files` / `tags`
   tables.

## Verification

1. Create an org-scoped resource while an organization is active; confirm
   `member_id` is populated.
2. `"own"` grant: another org member without `"all"` cannot mutate your row.
3. Leave the organization: member row has `deleted_at`; asset rows still
   reference the same `member_id` and show the snapshot `members.name`.
4. Re-accept an invite to the same org: same `members.id`, `deleted_at` cleared.
5. Org/team procedures without `activeOrganizationMemberId` return forbidden.
6. Personal billing / device flows still authorize on `userId`.
7. Run app typecheck / tests / build as you normally would after a framework
   bump.

## Rollback

- **Application code** can revert to the previous `@m5kdev/*` versions only if
  the database is also restored or the new columns remain unused.
- **Schema additions** (`members.name`, `deleted_at`, asset `member_id`) are
  forward-compatible; dropping them after soft-deletes exist loses attribution.
- Soft-deleted members cannot be recovered by rolling back application code
  alone if you later hard-delete rows — restore from backup if needed.

Prefer a forward fix (complete backfill, keep dual-write) over schema rollback.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Active organization context required` / forbidden on org procedures | Session missing `activeOrganizationMemberId`, or membership soft-deleted | Re-select org; confirm member `deleted_at` is null |
| `"own"` denies the creator | Entity missing `memberId` and legacy `userId` mismatch | Backfill `member_id`; pass both in `entities` |
| Duplicate membership on rejoin | App still hard-deletes members | Use framework remove/soft-delete path; revive on `(userId, organizationId)` |
| Empty member display after leave | `members.name` never backfilled | Run name backfill; ensure create/revive sets `name` |
| Lists empty after cutover | Context filter on `memberId` but rows not backfilled | Backfill, or temporarily allow dual-read / user filter |
