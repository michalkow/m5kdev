# Notification inbox in 0.36.0

## Summary

Notification is no longer device fan-out plus send logs. A **Notification** is a
persisted inbox instance owned by a **Member**, classified by a developer-declared
**Notification kind**. `send` always inserts that instance. Inbox visibility is
the in-app Channel at send time. Devices stay personal (**UserId**). Preferences
are per Membership.

This is **breaking** for apps that already registered `NotificationModule`:

- `enqueueSendToUser({ userId, ... })` is gone. Call `send({ memberId, kind, ... })`.
- App schema must export `notifications` and `notification_preferences` in
  addition to devices and send logs.
- Inbox and preference procedures require an organization actor (`memberId`).
- New frontend hooks and web-ui / Expo chrome. No `NotificationProvider`.

Capability docs: [Notification](/modules/notification). Complete
[Kernel Server events](/guides/v0.35.0-kernel-server-events-migration) in the
0.35.0 bump first so inbox invalidation can run.

There is **no** `create-m5kdev` registry transform. File add and three-way merge
are `m5kdev update`. Schema generation is **Manual**.

## Who needs this migration

- **Apps with `notifications` in `.m5kdev.json` features** (or that already
  register `NotificationModule` / export `notificationDevices` +
  `notificationSendLogs`).
- **Apps that called `enqueueSendToUser`** or assumed send logs were the inbox.
- **Web/Expo apps that want the Member inbox UI** after enabling the feature.

No action if the app never registered Notification and will not enable it.
New apps scaffolded on this release with `notifications` already get kinds,
tables, and Starter chrome.

## Prerequisites and upgrade order

Complete the [0.34.0 upgrades](/#upgrade-0-34-0) and the
[0.35.0 upgrades](/#upgrade-0-35-0) first, especially
[Kernel Server events](/guides/v0.35.0-kernel-server-events-migration)
(Auth emit + `ServerEventProvider`). Then bump to 0.36.0 for inbox.
Notification `send` emits `resource: "notification"`; the inbox hook listens
for that.

1. Commit or stash application changes.
2. Upgrade `@m5kdev/commons`, `@m5kdev/backend`, `@m5kdev/frontend`,
   `@m5kdev/web-ui`, `@m5kdev/expo` (if you use Expo), and `create-m5kdev`
   together (Managed catalog lockstep).
3. Run `m5kdev update --dry-run`, then `m5kdev update`.
4. Add Shared kinds, pass them into `NotificationModule`, export the new tables.
5. Generate and apply Drizzle migrations locally.
6. Replace send call sites. Compose inbox UI.

Always invoke an exact CLI release:

```sh
pnpm dlx create-m5kdev@0.36.0 update --dry-run
```

## What changed

- **Kinds** — App Shared `NOTIFICATION_KINDS` (`id`, `defaultChannels`, optional
  `delays`, `emailTemplate`). Not a table.
- **`NotificationService.send`** — inserts `notifications`, arms Channels from
  kind ∩ request ∩ not muted, `userEmit`s, enqueues delayed
  `notification.webPush` / `notification.mobilePush` / `notification.email`
  with `{ notificationId }`.
- **Tables** — `notifications` (MemberId, `visibleInInbox`, `armedChannels`,
  channel stamps, `readAt`); `notification_preferences` (mute rows, unique on
  member + kind + channel). Devices unchanged (UserId). Send logs gain
  `notificationId` and `channel`.
- **tRPC** — `listMyInbox`, `markRead`, `getMyPreferences`, `setMyPreference`
  (organization procedures). `sendTest` takes `memberId` + `kind`. Device
  procedures stay User-scoped.
- **Frontend** — `useNotificationInbox` / `useNotificationPreferences`. Inbox
  registers `useServerEventHandler` for `resource: "notification"`. No provider.
- **Web UI** — `NotificationSidebarInbox`, `NotificationInbox`,
  `NotificationPreferences`, `useWebPush`.
- **Expo** — `@m5kdev/expo` `useNativePush` + RN `NotificationInbox`.
- **Starter** — kinds in Shared; `NotificationModule({ kinds })`; sidebar inbox
  + `/notifications` prefs; Expo `/notifications`. Enable-push CTA only when
  not registered.

## Dependency and catalog changes

Pin these together on the Managed catalog to **0.36.0**:

- `@m5kdev/commons`
- `@m5kdev/backend`
- `@m5kdev/frontend`
- `@m5kdev/web-ui`
- `@m5kdev/expo` (Expo apps only)
- `create-m5kdev` (invoke with `pnpm dlx create-m5kdev@0.36.0`)

No new third-party catalog entries for the inbox itself. Web push still needs
the browser Push API and `/push-sw.js`. Native push still needs
`expo-notifications`. Redis remains required for delayed outbound jobs.

Node and pnpm engines are unchanged from 0.35.0.

## Migration steps

1. **Manual** — Upgrade catalog pins listed above to `0.36.0`. `pnpm install`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — may add Shared
   notification files and merge `schema.ts` / `app.ts` / web Router when those
   paths are merge-clean. Customized files often **Manual**.
3. **Manual** — Declare kinds and pass them into `NotificationModule`:

   ```ts
   new NotificationModule({ kinds: NOTIFICATION_KINDS }),
   ```

4. **Manual** — Export all four tables from App schema:

   ```ts
   export {
     notificationDevices,
     notificationPreferences,
     notificationSendLogs,
     notifications,
   } from "@m5kdev/backend/modules/notification/notification.db";
   ```

5. **Manual** — Run the project's Drizzle generate, review SQL, migrate. Do not
   hand-write migration files.
6. **Manual** — Replace send call sites:

   ```ts
   // before
   await this.service.notification.enqueueSendToUser({ userId, title, body });

   // after
   await this.service.notification.send({
     memberId,
     kind: "your.kind.id",
     title,
     body,
     data: null,
   });
   ```

   Use `ctx.actor.memberId` (or the Membership you are notifying). Do not send
   to a UserId.
7. **Conditional** (web) — Mount `NotificationSidebarInbox` in sidebar `content`.
   Pass `StarterWebPush` (or `useWebPush`) as `enablePush`. Add preferences
   route with `NotificationPreferences kinds={NOTIFICATION_KINDS} offerEmail`.
8. **Conditional** (Expo) — Add `@m5kdev/expo` and a notifications screen with
   `useNativePush` + `NotificationInbox`.
9. **Manual** — Confirm `ServerEventProvider` wraps the webapp. Inbox invalidation
   is inside `useNotificationInbox`; do not duplicate a `notification` handler
   unless you have extra queries.
10. **Conditional** (email Channel) — Keep `EmailModule` registered and set
    `emailTemplate` on those kinds.

## Database migration

**Do not create Drizzle migration files in-agent or by hand.** After exporting
the new tables:

1. Run the app generate command (Starter: `pnpm --filter ./apps/server drizzle:generate`).
2. Review the SQL.
3. Apply with the normal migrate path.

Expected new / changed tables (SQLite/libSQL naming):

| Table | Change |
| --- | --- |
| `notifications` | Add. `member_id` not null FK → `members.id` (`onDelete: cascade`); `user_id`; `kind`; `title`; `body`; `data`; `visible_in_inbox`; `armed_channels`; `web_pushed_at`; `mobile_pushed_at`; `emailed_at`; `read_at`; timestamps. |
| `notification_preferences` | Add. `member_id` not null FK → `members.id`; `kind`; `channel`; unique `(member_id, kind, channel)`. |
| `notification_send_logs` | `notification_id` is **NOT NULL** (FK → `notifications.id`) and `channel` is required. Existing device-era rows cannot satisfy that without a Notification id. Truncate or drop send logs before migrate unless you have a product-specific backfill. Do not invent inbox rows from old logs. |
| `notification_devices` | Unchanged (UserId). |

There is no required data backfill for empty inboxes. Do not invent Notification
rows from old send logs unless you have a product-specific mapping.

## Environment and deployment changes

No new required env for in-app-only kinds.

- **VAPID** — required to subscribe browsers when a kind offers `web-push`.
- **APNs / FCM** — required for `mobile-push`.
- **Redis** — required for delayed outbound jobs (same as Workflow).
- **Workers** — HTTP and worker processes must share Redis if jobs run off-request.
- **HTTPS** — browsers require a secure context for Push (localhost excepted).

Roll out schema migrate **before** or **with** code that inserts `notifications`.
Old `enqueueSendToUser` callers will not compile against 0.36.0.

## Verification

In this repo:

```sh
pnpm --filter @m5kdev/backend test src/modules/notification/notification.service.test.ts
pnpm --filter @m5kdev/frontend test src/modules/notification/notification.query.test.ts
```

In the app:

- Active Organization: sidebar inbox opens; empty state is fine.
- `send` (or admin `sendTest` with that Membership's `memberId`): row appears
  for that org only; switching Organization hides it.
- Mute in-app for a kind: a later `send` still inserts but `visibleInInbox` is
  false.
- Web: enable-push chip shows until this browser is registered, then hides.
  It is not in the AppShell header.
- Logged-in `GET /events` is 200 SSE; a send from another request refreshes
  the inbox without a full reload.
- `pnpm check-types` / `pnpm lint` succeed.

## Rollback

Revert the `@m5kdev/*` / `create-m5kdev` bump and restore previous send call
sites. New tables can remain unused; dropping them after instances exist loses
inbox history. Prefer a forward fix over dropping `notifications`.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Unknown Notification kind` | Kind id not in `NotificationModule({ kinds })` | Add it to Shared kinds and pass the same array into the module |
| Inbox empty in every org | `visibleInInbox` false (in-app muted or not on the kind) | Offer `in-app` on the kind; check preferences |
| Inbox shows another org's rows | Client not keying by `activeOrganizationId` | Use `useNotificationInbox` / `notificationInboxQueryKey` |
| `FORBIDDEN` on `listMyInbox` | No organization actor / `memberId` | Select an Organization; require `organizationProcedure` |
| Push never arrives | Job not running, no Redis, or Channel not armed | Start worker + Redis; confirm kind `defaultChannels` and mutes |
| Enable-push stays in the header | App still mounts `StarterWebPush` on `AppShell.header` | Move it to inbox `enablePush` and `/notifications` |
| Types cannot find `@m5kdev/expo` | Expo package not pinned | Add `@m5kdev/expo` on the Managed catalog at 0.36.0 |
| Inbox remains after disabling `notifications` | Layout inbox was not inside `m5k:notifications` markers | Wrap the import and `NotificationSidebarInbox` mount, or remove them |
