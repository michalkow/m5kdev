# Subscription per Stripe environment in 0.38.15

## Summary

A Subscription is one mutable local row per Organization per Stripe environment
(`production` | `sandbox`), the same switch as the Plan catalog and Stripe
Customer. This process only reads, upserts, Checkouts, Seat-bills, and cancels
its environment's row. A sandbox ACCESS_STATUS does not grant production.

There is **no** `create-m5kdev` registry transform. Schema generation is
**Manual**. Data stamp SQL is **Manual** (Kernel does not auto-backfill).
Capability docs: [Billing module](/modules/billing). Decision: ADR-0024
(`docs/adr/0024-subscription-per-stripe-environment.md`).

## Who needs this migration

- **Apps that have a `subscriptions` table** (they register `BillingModule` or
  export the Billing schema). Without the column, reads fail with
  `no such column: environment`.
- **Apps that share an Organization database between production and sandbox.**
  After 0.38.11, Customer ids split; Subscription did not. Production Billing
  Module admin can show sandbox Plan, Price, Trial, and Coupon with an empty
  production Customer. Stamp SQL below fixes existing rows.
- **Starter.** No BillingModule and no `subscriptions` table. No action.

## Prerequisites and upgrade order

Complete the [0.38.13 upgrade](/#upgrade-0-38-13) first (which includes 0.38.11
Customer split).

1. Commit or stash application changes.
2. Upgrade `@m5kdev/commons`, `@m5kdev/backend`, `@m5kdev/frontend`,
   `@m5kdev/web-ui`, and `create-m5kdev` together to `0.38.15`.
3. Generate and apply the Drizzle migration.
4. Stamp and collapse existing Subscription rows (below).

```sh
pnpm dlx create-m5kdev@0.38.15 update --dry-run
```

## What changed

Customer ids and Plan catalogs already split by environment. The local
Subscription was one latest row per Organization, so a sandbox webhook filled
or overwrote that row and production read it. Paywall used the same latest
row.

Now `subscriptions.environment` is `production` | `sandbox` (nullable for
unmatched leftovers). New writes always set the catalog environment. Unique
one row per `(reference_id, environment)` when environment is not null.
Checkout "has none" means none in this environment. Organization delete
cancels only the current-env Stripe Subscription.

`billingExempt` stays Organization-wide.

## Dependency and catalog changes

No new dependencies. Pin `@m5kdev/commons`, `@m5kdev/backend`,
`@m5kdev/frontend`, `@m5kdev/web-ui`, and `create-m5kdev` to **0.38.15**
together. Root `pnpm-workspace.yaml` and
`packages/cli/root-templates/pnpm-workspace.yaml.tpl` gain no pins. Node.js and
pnpm engines are unchanged.

## Migration steps

1. **Manual** — Upgrade the packages to `0.38.15`; `pnpm install`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — nothing for this
   id (registry empty).
3. **Manual** — Generate and apply the Drizzle migration (see below).
4. **Manual** — Stamp environment from Organization Customer ids, then collapse
   extras. Run after the column exists. Do not run Kernel boot as a backfill.

```sql
UPDATE subscriptions
SET environment = 'production'
WHERE environment IS NULL
  AND stripe_customer_id IN (
    SELECT stripe_customer_id
    FROM organizations
    WHERE stripe_customer_id IS NOT NULL
  );

UPDATE subscriptions
SET environment = 'sandbox'
WHERE environment IS NULL
  AND stripe_customer_id IN (
    SELECT stripe_sandbox_customer_id
    FROM organizations
    WHERE stripe_sandbox_customer_id IS NOT NULL
  );

DELETE FROM subscriptions
WHERE environment IS NOT NULL
  AND id NOT IN (
    SELECT id
    FROM subscriptions AS s
    WHERE s.environment IS NOT NULL
      AND s.created_at = (
        SELECT MAX(t.created_at)
        FROM subscriptions AS t
        WHERE t.reference_id = s.reference_id
          AND t.environment = s.environment
      )
  );
```

Unmatched rows stay `environment` null and are unreadable until a current-env
sync claims them (same Stripe Subscription id) or inserts a new row.

## Database migration

Generate and apply with the project's command (do not hand-write migration
files):

```sh
pnpm --filter ./apps/server drizzle:generate
pnpm --filter ./apps/server drizzle:migrate
```

Expected schema: nullable `subscriptions.environment` (`production` |
`sandbox`) and a unique pair `(reference_id, environment)` for non-null
environment. The stamp/collapse SQL is a data change, not a schema migration.

## Environment and deployment changes

No new env vars. Roll the schema first, then processes, then the stamp SQL.
Until rows are stamped, production hides null-environment and sandbox-stamped
rows; live access needs production-stamped ACCESS_STATUS (or `billingExempt`).

## Verification

- Production Billing Module admin: Organizations with only a sandbox
  Subscription show empty Customer (if no production Customer) and no Plan /
  Price / status / Coupon.
- Sandbox admin still shows that sandbox Subscription.
- A newly created production Subscription does not replace the sandbox row.
- Production paywall ignores sandbox `trialing` / `active` / `past_due`.
- Organization delete from production cancels only the production Stripe
  Subscription.

In this repo: `packages/backend/src/modules/billing/tests/billing.service.test.ts`.

## Rollback

The column is additive; older packages ignore it. To undo a mistaken stamp:

```sql
UPDATE subscriptions SET environment = NULL;
```

Do not drop the column as a rollback of this release.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `no such column: environment` | Migration not applied | Generate and migrate |
| Production still shows sandbox Plan/Price | Rows not stamped | Run stamp SQL after the column exists |
| Production paywall closed for a paying org | Production row still null environment | Stamp from `organizations.stripe_customer_id` |
| Unique constraint on `(reference_id, environment)` | Extra historical rows | Run the collapse `DELETE` |
| Sandbox admin empty after stamp | Row matched production Customer only | Confirm `stripe_sandbox_customer_id` and re-sync sandbox |
