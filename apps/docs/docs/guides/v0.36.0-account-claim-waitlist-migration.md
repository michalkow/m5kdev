# Account claim and Waitlist in 0.36.0

## Summary

**Account claim** is its own resource. Waitlist no longer stores claims (no
`type` discriminator, no `claim_user_id` / `claimed_at` / `claimed_email`).
Magic links reference `account_claims`. Existing Account claim Procedures
keep their names and now read and write that table.

**Waitlist codes** are Waitlist, not Invitation. `createInvitationCode` is
renamed to `createWaitlistCode`. Users may mint up to 3 reusable codes
(separate from `inviteToWaitlist`'s cap of 3). Admin people lists never
include other people's codes. Accepting a Waitlist code creates the User
first; only then is the Waitlist row marked accepted, so a failed signup does
not consume the code.

There is **no** framework data backfill from Waitlist claim rows into
`account_claims`. Apps that already provisioned claims must copy those rows
**before** applying a generated migration that drops Waitlist claim columns.

There is **no** `create-m5kdev` registry transform. Schema generation is
**Manual**. Web-ui invite-friends already calls `createWaitlistCode`; forked
copies are **Manual**.

Capability docs: [Auth](/modules/auth).

## Who needs this migration

- **Every Auth app** that bumps `@m5kdev/backend` to 0.36.0. App schema must
  export `accountClaims`. Waitlist shape changes for all of them.
- **Apps that stored Account claim on `waitlist` with `type: "ACCOUNT_CLAIM"`**
  (or that have `account_claim_magic_links.claim_id` pointing at Waitlist ids).
- **Apps that called `auth.createInvitationCode`** (tRPC or service).
- **Forked invite-friends UI** still using the old procedure name.

No action if the app never registered Auth. New apps scaffolded on this
release already export `accountClaims` and mint Waitlist codes under the new
name.

   into `account_claims` and remap magic-link `claim_id` (see Database

4. Export `accountClaims`. Generate and apply Drizzle migrations.
5. Rename `createInvitationCode` call sites to `createWaitlistCode`.

Always invoke an exact CLI release:

```sh

```

## What changed

### Account claim table

- New table `account_claims`: `claim_user_id`, `status`, `code`,
  `expires_at`, `claimed_at`, `claimed_email`, timestamps.
- `account_claim_magic_links.claim_id` FKs to `account_claims.id`
  (`onDelete: cascade`), not `waitlist.id`.
- Waitlist dropped `type`, `claim_user_id`, `claimed_at`, `claimed_email`.
  Remaining Waitlist columns: identity, `status`, `code`, `expires_at`,
  `user_id`.
- Unused `createClaimableProvisionedUser` helper is gone. Admin create /
  list / magic-link / self-claim Procedures stay:
  `createAccountClaimCode`, `listAccountClaims`,
  `generateAccountClaimMagicLink`, `listAccountClaimMagicLinks`,
  `getMyAccountClaimStatus`, `setMyAccountClaimEmail`,
  `acceptMyAccountClaim`.

### Waitlist codes

- tRPC / service: `createWaitlistCode` replaces `createInvitationCode`.
- Mint cap: 3 reusable codes per User (`waitlist` rows with `userId` set and
  `email` null). Independent of `inviteToWaitlist` (still 3 emailed invites).
- `listWaitlist` (the User's own rows) includes `code`. `listAdminWaitlist`
  / `joinWaitlist` omit other people's codes (`output.single` omits `code`
  and `expiresAt`).
- Accept path: User is created first; the Waitlist row is marked accepted
  only after that succeeds.

## Migration steps

1. **Manual** — Upgrade catalog pins listed above to `0.36.0`. `pnpm install`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — may merge
   Starter `schema.ts` if that path is merge-clean. There is no registry
   `id` `0.36.0-account-claim-waitlist`.
3. **Conditional** (existing Account claim rows) — **before** generate/apply,
   copy Waitlist claims into `account_claims` and remap magic links. A naive
   generated rebuild (Starter dogfood has no claim data) creates an empty
   `account_claims` table and copies old `claim_id` values that still point
   at Waitlist ids. That leaves orphan magic links. See Database migration.
4. **Manual** — Export the new table:

   ```ts
   export {
     accountClaimMagicLinks,
     accountClaims,
     // ...other Auth tables, including waitlist
   } from "@m5kdev/backend/modules/auth/auth.db";
   ```

5. **Manual** — Generate Drizzle migrations with the project's usual command
   (do not hand-write SQL). Apply them after any claim backfill. Expected
   schema:
   - `CREATE TABLE account_claims (...)`
   - `account_claim_magic_links.claim_id` FK → `account_claims.id`
   - `waitlist` without `type` / `claim_user_id` / `claimed_at` /
     `claimed_email`
6. **Manual** — Replace call sites:

   ```ts
   // before
   trpc.auth.createInvitationCode.mutate({ name });

   // after
   trpc.auth.createWaitlistCode.mutate({ name });
   ```

   Account claim Procedures keep their names. Do not filter Waitlist lists
   on `type: "ACCOUNT_CLAIM"`.
7. **Conditional** (forked invite-friends UI) — switch to
   `AuthUserInviteFriends` or the same tRPC. Minted-code quota is 3, separate
   from emailed invites.

## Database migration

Schema change. **Do not** create Drizzle migration files by hand. Run the
project's migration generation command, review the SQL, then apply.

**No automatic backfill.** If `waitlist.type = 'ACCOUNT_CLAIM'` (or
`claim_user_id` is set) exists in production:

1. Create `account_claims` with the same ids you will keep on magic links
   (simplest: reuse the Waitlist row id as `account_claims.id` so
   `claim_id` values stay valid), mapping:
   - `claim_user_id` ← `waitlist.claim_user_id`
   - `status` ← Waitlist claim status
   - `code` / `expires_at` / `claimed_at` / `claimed_email`
2. Confirm `account_claim_magic_links.claim_id` matches those ids.
3. Then generate/apply so Waitlist claim columns can drop.

If you have **no** Account claim rows, generate and apply as usual. Empty
`account_claims` is correct.

Waitlist signup rows (`type` default `WAITLIST`) stay on `waitlist`. Do not
copy them into `account_claims`.

## Environment and deployment changes

No new required env. Waitlist and Account claim email still need EmailModule
and `app.urls.web`.

- **Rollout order** — backfill (if any), apply Drizzle, then deploy backend,
  then web. New code will not read `waitlist.type`.
- **In-flight claim magic links** — valid only if `claim_id` points at
  `account_claims`. Re-issue links if you skipped the backfill.
- **Workers** — none.

In the app:

- Magic link redeem still attaches the provisioned User.
- Invite-friends: minting a code calls `createWaitlistCode`; a fourth mint
  fails; `inviteToWaitlist` can still send up to 3 emails.

- Failed signup with a Waitlist code leaves the code usable.
- `pnpm check-types` / `pnpm lint` succeed; `createInvitationCode` is gone.

## Rollback

Revert the `@m5kdev/*` / `create-m5kdev` bump and restore previous schema
exports from git. If `account_claims` already has rows, do not drop it to
return to Waitlist-typed claims without a restore plan. Prefer a forward
fix: keep the new table.

## Troubleshooting

- **Type error on `createInvitationCode`** — renamed to `createWaitlistCode`.
- **`Unknown table account_claims` / schema export missing** — add
  `accountClaims` to App schema, then generate.
- **Magic link 404 / FK errors after migrate** — `claim_id` still points at
  Waitlist ids. Backfill `account_claims` with those ids or re-issue links.
- **Admin Waitlist still filters `ACCOUNT_CLAIM`** — that discriminator is
  gone. Use `listAccountClaims`.
- **Fourth Waitlist code refused** — mint cap is 3 per User. Email invites
  are a separate cap of 3.
- **Join Waitlist response includes `code`** — should not; join uses
  `output.single`. Check you are not returning `output.full` from a forked
  handler.
