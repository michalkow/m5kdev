# Billing Coupons, sandbox Stripe Customer, and required catalog environment in 0.38.11

## Summary

Billing Module admin no longer has a Complimentary action. An AdminActor
applies, replaces, or removes one Coupon that already exists in the Stripe
account, creates a Subscription on a catalog Price with an optional Coupon,
creates a missing Stripe Customer, and sets Organization currency only when it
is null. A failed invoice without a payment method now stays `past_due` with
access; Admin cancel is the cutoff.

The Organization gains a second Stripe Customer id for sandbox
(`organizations.stripe_sandbox_customer_id`). Billing picks production or
sandbox from `ResolvedStripePlans.environment`, the same switch as the Plan
catalog, so a sandbox Customer never overwrites the live one.

There is **no** `create-m5kdev` registry transform. Schema generation is
**Manual**. Capability docs: [Billing module](/modules/billing). Decision:
ADR-0022 (`docs/adr/0022-complimentary-billing-admin.md`).

## Who needs this migration

- **Every app.** `organizations` is an Auth table; the new column must exist or
  Organization reads fail with `no such column: stripe_sandbox_customer_id`.
- **Apps that register `BillingModule`.** They must pass `environment` on
  `ResolvedStripePlans` (automatic when the catalog comes from
  `getEnvironmentPlans`) and move sandbox Customer ids in sandbox databases.
- **Apps that call `billing.enrollComplimentary` or
  `billing.removeComplimentary`.** Those Procedures are removed.

No action beyond the schema generate if the app never registered Billing.
`create-m5kdev` `billing` still records the feature id only.

## Prerequisites and upgrade order

Complete the [0.38.9 upgrade](/#upgrade-0-38-9) first.

1. Commit or stash application changes.
2. Upgrade `@m5kdev/commons`, `@m5kdev/backend`, `@m5kdev/frontend`,
   `@m5kdev/web-ui`, and `create-m5kdev` together to `0.38.11`.
3. Generate and apply the Drizzle migration.
4. In each **sandbox** database, move existing Customer ids (below).
5. Replace any Complimentary admin calls.

```sh
pnpm dlx create-m5kdev@0.38.11 update --dry-run
```

## What changed

### Catalog environment

`ResolvedStripePlans.environment: "production" | "sandbox"` is required.
`getEnvironmentPlans(plansConfig, process.env.NODE_ENV)` sets it
(`"production"` only when the environment argument is `"production"`). A
hand-built `ResolvedStripePlans` object must add it.

### Stripe Customer per environment

| Environment | Column Billing reads and writes |
| --- | --- |
| `production` | `organizations.stripe_customer_id` |
| `sandbox` | `organizations.stripe_sandbox_customer_id` |

Customer create, webhook Organization lookup, invoices, Checkout, and Billing
Portal all use the current environment's column. The other column is never
written. Both are hidden from Organization API output.

### Coupons and admin Procedures

Removed: `billing.enrollComplimentary`, `billing.removeComplimentary`. Kernel no
longer find-or-creates `m5k_comp_*` Coupons.

Added (AdminActor, `adminProcedure`, input carries `organizationId`):

| Procedure | Grant action |
| --- | --- |
| `billing.listAdminCoupons` | `read` |
| `billing.createAdminCustomer` | `write` |
| `billing.setAdminOrganizationCurrency` | `write` |
| `billing.createAdminSubscription` | `write` |
| `billing.applyAdminCoupon` | `write` |
| `billing.removeAdminCoupon` | `write` |

`billing.listAdminOrganizationBilling` rows add `stripeCustomerId` (current
environment), `openSubscription`, and `coupon`, and drop nothing.
`billing.cancelAdminSubscription` is unchanged. Grant action names are
unchanged (`read` / `write` / `delete`), so custom Billing grants need no edit.

`subscriptions.discounts` now stores Stripe Coupon ids (from each Discount's
`source.coupon`), not Discount ids.

### Failed invoices

`invoice.payment_failed` only re-syncs. Kernel no longer cancels when the
Customer has no payment method. Removing a Coupon never cancels.

## Dependency and catalog changes

No new dependencies. Pin `@m5kdev/commons`, `@m5kdev/backend`,
`@m5kdev/frontend`, `@m5kdev/web-ui`, and `create-m5kdev` to **0.38.11**
together. Root `pnpm-workspace.yaml` and
`packages/cli/root-templates/pnpm-workspace.yaml.tpl` gain no pins. Node.js and
pnpm engines are unchanged.

## Migration steps

1. **Manual** — Upgrade the five packages to `0.38.11`; `pnpm install`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — nothing Billing-specific.
3. **Manual** — Generate and apply the Drizzle migration (see below).
4. **Conditional (sandbox databases only)** — Move sandbox Customer ids, then
   clear the production column in that database:

```sql
UPDATE organizations
SET stripe_sandbox_customer_id = stripe_customer_id,
    stripe_customer_id = NULL
WHERE stripe_customer_id IS NOT NULL
  AND stripe_sandbox_customer_id IS NULL;
```

   Run this **only** where Billing runs with sandbox Stripe keys. Never run it
   against production.

5. **Conditional** — Hand-built catalog:

```ts
const resolved: ResolvedStripePlans = {
  environment: process.env.NODE_ENV === "production" ? "production" : "sandbox",
  plans,
  trialPlanName,
  trialRequiresPaymentMethod: false,
  defaultCurrency: "usd",
  seatBilling: false,
  nonBillableRoleKeys: [],
};
```

6. **Conditional** — Replace Complimentary calls. Create the 100% Coupon in the
   Stripe Dashboard, then call `billing.createAdminSubscription` with
   `couponId` when there is no Subscription, or `billing.applyAdminCoupon` on an
   existing one.

## Database migration

Generate and apply with the project's command (do not hand-write migration files):

```sh
pnpm --filter ./apps/server drizzle:generate
pnpm --filter ./apps/server drizzle:migrate
```

Expected schema: nullable `organizations.stripe_sandbox_customer_id` with a
unique index. The sandbox data move in step 4 is a data change, not a schema
migration; run it after the column exists.

## Environment and deployment changes

No new env vars. Make sure sandbox processes pass a non-`production` value to
`getEnvironmentPlans` (for example `NODE_ENV=staging`) and production passes
`production`. Roll the schema first, then the sandbox data move, then the new
processes.

## Verification

- App boot succeeds; Organization reads do not error on the new column.
- In sandbox, `billing.createAdminCustomer` writes `stripe_sandbox_customer_id`
  and leaves `stripe_customer_id` unchanged.
- Existing sandbox webhooks still resolve their Organization after the data move.
- Billing Module admin lists Coupons from Stripe and applies one; the Coupon
  column shows its name and percent or amount.
- A failed invoice without a card leaves the Subscription `past_due`.

In this repo: `packages/backend/src/modules/billing/tests/billing.service.test.ts`.

## Rollback

The column is additive; older packages ignore it. If you ran the sandbox data
move, copy ids back before rolling sandbox to 0.38.10:

```sql
UPDATE organizations
SET stripe_customer_id = stripe_sandbox_customer_id
WHERE stripe_sandbox_customer_id IS NOT NULL
  AND stripe_customer_id IS NULL;
```

Production needs no data rollback. On 0.38.10, `invoice.payment_failed`
without a card cancels again.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `no such column: stripe_sandbox_customer_id` | Migration not applied | Generate and migrate |
| Sandbox webhook `Organization not found` | Sandbox ids still in `stripe_customer_id` | Run the sandbox data move |
| Duplicate Stripe Customers in sandbox | Same cause; Kernel created a new Customer | Run the move; archive duplicates in Stripe |
| Type error: `environment` missing | Hand-built `ResolvedStripePlans` | Add `environment` or use `getEnvironmentPlans` |
| Coupon column shows a bare id | Row synced before 0.38.11 stored a Discount id | Re-sync (any webhook, or `syncOrganizationSubscription`) |
| Coupon picker empty | No valid Coupons in the Stripe account | Create Coupons in the Stripe Dashboard |
