# Catalog lockstep and boundary peers in 0.33.0

:::note Open question
Confirm the published release number before linking this guide from release
notes. Packages in the monorepo currently report `0.32.9`; rename the file and
`migration.id` / `target_version` if the ship version differs from `0.33.0`.
:::

## Summary

Scaffolded apps share the framework release’s third-party pins. Boundary
libraries (`drizzle-orm`, `zod`, `react`, and the rest of the closed set) are
now **peers** of published `@m5kdev/*` packages so the app and Kernel share one
physical copy. Two copies of `drizzle-orm` — even the same version — make
Drizzle `Column` types incompatible and break FK `.references()`.

`m5kdev update` advances **managed** catalog pins with the release. Those pins
live in the named pnpm catalog `catalogs.m5kdev`; manifests use
`catalog:m5kdev`. Do **not** run `pnpm update --latest` (or any blanket latest
bump) for stack libraries. App-owned keys stay in the default `catalog:`.
Local+upstream edits to a managed key are conflicts.

There is **no** `create-m5kdev` registry transform. Catalog merge is the
existing updater. Peer and OpenTelemetry pins on app manifests are **Manual**
or **Conditional**.

Decision record: ADR-0004 (`docs/adr/0004-catalog-lockstep-and-boundary-peers.md`).

## Who needs this migration

- **Every managed app** that consumes `@m5kdev/backend`, `@m5kdev/commons`,
  `@m5kdev/frontend`, or `@m5kdev/web-ui` from the `0.33.0` line.
- Apps that still nested their own `drizzle-orm` (or another boundary library)
  at a different version than the catalog — they must move to the catalog pin.
- Apps that never declared a boundary library because it was nested under
  `@m5kdev/*` — they must add it as a direct `catalog:m5kdev` dependency.

Unmanaged apps that pin `@m5kdev/*` without a pnpm catalog still need the same
peer installs at the versions this release tested.

## Prerequisites and upgrade order

1. Finish earlier framework migrations your app still needs
   ([managed consumer updates](/guides/v0.31.0-managed-consumer-updates-migration)
   if the app is not enrolled).
2. Upgrade `create-m5kdev` and the `@m5kdev/*` packages together to the
   `0.33.0` line. Do not mix an older Kernel with a newer app `drizzle-orm`.
3. Run `m5kdev update` so managed catalog pins follow the release, then add
   any missing peers and the server OpenTelemetry pin.
4. `pnpm install` and typecheck. Do not follow that with `pnpm update --latest`.

## What changed

| Layer | Change |
| --- | --- |
| `@m5kdev/backend` | Boundary libraries are `peerDependencies` (kept as `devDependencies` in the monorepo). Nested Kernel deps (pino, BullMQ, AWS, OTEL exporters) stay `dependencies`. |
| `@m5kdev/commons` | `zod` is a peer. |
| `@m5kdev/frontend` | `@trpc/client`, `@trpc/server`, `better-auth`, `react`, `react-dom`, `zod` are peers ( `@trpc/server` already was). |
| `@m5kdev/web-ui` | `@heroui/react`, `nuqs`, `react`, `react-dom`, `zod` are peers. |
| Starter server | Declares `@opentelemetry/api: catalog:` so drizzle’s optional OTEL peer cannot split a second `drizzle-orm`. |
| Starter / Expo | Catalogued third-parties use `catalog:` (including React). Catalog React is `19.2.3`. |
| CLI | Generated apps write `catalogs.m5kdev` and `catalog:m5kdev`. `doctor` still errors on `CATALOG_VERSION_MISMATCH`. `update` three-way-merges the named catalog and leaves the default `catalog:` for app-owned pins. |

Boundary libraries (closed set): `drizzle-orm`, `drizzle-zod`, `zod`,
`neverthrow`, `@trpc/server`, `@trpc/client`, `react`, `react-dom`,
`better-auth`, `express`, `@heroui/react`, `nuqs`.

OpenTelemetry is **not** in that set. Do not add pnpm `overrides` for it.

| Path | Existing app |
| --- | --- |
| `pnpm-workspace.yaml` | **Automatic** via `m5kdev update` catalog merge when the file is managed and the key was not customized. |

| `apps/<app>/webapp/package.json` | Validate only if Starter-aligned; add missing web-ui / frontend peers. |

customized `package.json` wholesale.

## Migration steps

### 1. Upgrade the CLI and framework packages — Manual

Install the `0.33.0` line of `create-m5kdev` and the `@m5kdev/*` packages
together. Invoke an exact CLI release (`pnpm dlx create-m5kdev@0.33.0`), not a
floating tag.

### 2. Advance managed catalog pins — Automatic (`m5kdev update` apply)

```sh
pnpm dlx create-m5kdev@0.33.0 update --dry-run
pnpm dlx create-m5kdev@0.33.0 update
```

This three-way-merges managed catalog keys. App-owned keys stay. A key you
changed locally that also changed upstream is a conflict — resolve it to the
framework pin for stack libraries, or keep the local value only for true
app-owned extras.

`m5kdev doctor` still reports `CATALOG_VERSION_MISMATCH` as an error.

### 3. Declare missing boundary peers — Conditional

If `pnpm install` warns that a peer is missing, add it with `catalog:m5kdev` on the
app package that imports `@m5kdev/*` (usually `server` and `webapp`). Starter
already lists them. Do not nest a second version in `dependencies` of an
`@m5kdev/*` wrapper.

### 4. Pin `@opentelemetry/api` on the server — Automatic (`m5kdev update` apply) or Conditional

When `apps/<app>/server/package.json` still matches the previous template,
`m5kdev update` three-way-merges:

```json
"@opentelemetry/api": "catalog:m5kdev"
```

If that file was customized, add the line yourself. Do not use pnpm
`overrides` for OpenTelemetry.

### 5. Install without a blanket latest bump — Manual

```sh
pnpm install
```

Do **not** run `pnpm update --latest` (or `pnpm update` without a package name)
to “refresh” drizzle, React, or other stack libraries. Those pins move only
with a framework release via `m5kdev update`.

## Database migration

None. This is install and TypeScript identity, not schema.

## Environment and deployment changes

None. No new environment variables. Deploy `@m5kdev/*` packages and the
catalog-pinned peers together so the server does not typecheck against a
different `drizzle-orm` than the Kernel.

## Verification

- `pnpm install` succeeds with `catalogMode: strict`.
- `pnpm check-types` on the server: tables that `.references()` Kernel auth
  columns typecheck.
- `m5kdev doctor` has no `CATALOG_VERSION_MISMATCH` for managed keys.
- `pnpm why drizzle-orm` (from the server package) shows one version, not two
  physical copies under `@m5kdev/backend` and the app.
- Credentialed app boot still works (peers are present at runtime, not only
  types).

```sh
pnpm install
pnpm check-types
pnpm dlx create-m5kdev@0.33.0 doctor
```

## Rollback

- **Packages:** pin the previous `@m5kdev/*` line. Nested drizzle returns;
  FK type errors may disappear for the wrong reason (two copies again).
- **Catalog:** restore the previous managed catalog snapshot from git. No
  database rollback.
- **Peers:** leftover `catalog:` entries on the app are harmless on an older
  Kernel that still nests those libraries.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Property 'config' is protected` / incompatible `Column` on `.references()` | Two `drizzle-orm` copies (often split by `@opentelemetry/api` 1.9.0 vs 1.9.1) | Pin server `@opentelemetry/api` to `catalog:` (`1.9.0`); do not override |
| Peer missing at `pnpm install` | Relied on a nested `@m5kdev/*` dependency | Add the library as `catalog:` on the app package |
| `CATALOG_VERSION_MISMATCH` | Local catalog pin ≠ managed snapshot | `m5kdev update`, or restore the managed pin; extra keys are fine |
| Update conflict on a catalog key | You changed it and the release changed it | Take the framework pin for stack libraries |
| Expo cannot resolve `react` | Exact-pinned React instead of `catalog:` | Use `catalog:`; the catalog pin is `19.2.3` |
| `pnpm update --latest` moved drizzle | Blanket latest bump | Revert the catalog; use `m5kdev update` next time |
