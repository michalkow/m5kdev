# Docker, Fly.io, and Node 24 in 0.34.0

:::note Open question
Confirm the published release number before linking this guide from release
notes. Packages in the monorepo currently report `0.33.0`; rename the file and
`migration.id` / `target_version` if the ship version differs from `0.34.0`.
:::

## Summary

Starter now ships Docker images and a Fly.io adapter: product Deploy home under
`apps/shared`, a required Landing package, and root `app:deploy` /
`landing:deploy` wrappers. The Kernel can serve a baked SPA via
`spa: { root: "./client" }`. Engines are **Node.js >= 24**. There is **no**
`create-m5kdev` registry transform. `fly.toml` and `.env.production` are
**ignored** on update.

## Who needs this migration

- Every generated app moving to this release must satisfy Node `>=24`.
- Apps that want Fly/Docker copy the new files once (update will not merge
  `fly.toml`).
- Apps that already deploy elsewhere can keep their host; the Dockerfile is the
  portable artifact. Fly is the shipped adapter, not a second required host.

## Prerequisites and upgrade order

Complete [Kernel Database commands in 0.34.0](./v0.34.0-kernel-database-commands-migration.md)
and [Core Modules and Optional Backend Module packages](./v0.34.0-core-optional-backend-modules-migration.md)
in the same release when those diffs apply.

1. Install Node.js 24 (do not pin a patch like `24.11.0` in engines).
2. Commit or stash application changes.
3. Upgrade `@m5kdev/backend` and `create-m5kdev` together (Managed catalog lockstep).
4. Run `m5kdev update --dry-run`, then `m5kdev update`.
5. Copy Deploy home / Landing files if you want Fly, then fill `.env.production`.

Always invoke an exact CLI release once the number is confirmed.

## What changed

- Root and Template `engines.node` is `>=24`. Images use `FROM node:24-slim`.
- Kernel `createBackendApp({ spa: { root } })` serves `express.static` + SPA
  fallback when `root` exists and is a directory. Starter sets `./client`.
- Product Dockerfile + `fly.toml` live in Deploy home (`apps/shared`). Landing
  is a separate Vite SPA with its own Dockerfile and `fly.toml`.
- One root `.dockerignore`. `.env*` never enters the image.
- `create-m5kdev update` ignores `**/fly.toml` and `**/.env.production`.

## Dependency and catalog changes

No new third-party catalog entries required for apps that already have HeroUI,
React, Vite, and react-router (Landing uses that subset). `vite` is a Landing
**dependency** so `vite preview` works in the production image.

`@m5kdev/backend` and `create-m5kdev` move together on the Managed catalog.
pnpm stays `packageManager` `pnpm@10.13.1`.

Node.js requirement changes from `>=22` to `>=24`.

## Migration steps

1. **Manual** — Switch the machine and CI that run this app to Node 24. Set
   `engines.node` to `>=24`. Do not pin `24.11.0`.
2. **Automatic** (`m5kdev update` apply, after `--dry-run`) — merges Dockerfiles,
   examples, wrappers, and Kernel `spa.root` when those files are unmodified.
   Does **not** write `fly.toml` or `.env.production` (ignore policy).
3. **Manual** — Copy `apps/shared/fly.toml` and `apps/landing/fly.toml` from a
   fresh scaffold if you do not have them. Set `app =` to your Fly app names.
   Update will not overwrite an existing `fly.toml`.
4. **Manual** — Copy `.env.production.example` to `.env.production` (gitignored).
   Set `DATABASE_URL=file:/app/data/local.db` on Fly, and `REDIS_URL` as a
   runtime secret.
5. **Manual** — `fly volumes create libsql_data` for the product app, then
   `pnpm app:secrets` / `pnpm landing:secrets` and `pnpm app:deploy` /
   `pnpm landing:deploy`.
6. **Conditional** — Expo-only apps keep Landing and the server image; webapp
   Dockerfile stages are stripped at create time. Do not add a per-app
   dockerignore.

## Database migration

None. Table definitions are unchanged. Do not hand-write SQL.

## Environment and deployment changes

New optional production files: `apps/shared/.env.production` and
`apps/landing/.env.production`. Product example uses
`DATABASE_URL=file:/app/data/local.db`. `REDIS_URL` is documented as a runtime
secret. `VITE_*` are build-time (baked into the SPA).

See [Deploy with Docker and Fly.io](./fly-deploy.md).

## Verification

- `node -v` reports v24.
- `pnpm check-types` and `pnpm lint` succeed, including `apps/landing`.
- Fresh `create-m5kdev` web scaffold has root `.dockerignore`, Deploy home
  files, Landing, and `engines.node` `>=24`.
- `create-m5kdev update --dry-run` does not propose changing `fly.toml` or
  `.env.production`.

## Rollback

- Revert `spa.root` if you must run an older Kernel; omit the option and the
  Kernel will not mount a SPA.
- Fly apps and volumes are not removed by rolling back the repo. Destroy them
  in Fly if you abandon the adapter.
- Engines can be lowered only if you also stop using `node:24-slim` images.

## Troubleshooting

- **Missing `.env.production`** — copy the sibling `.env.production.example`.
- **SPA 404 in production** — confirm the image copied webapp `dist` to
  `./client` and `spa.root` is `./client`. Local dev has no `./client`; that is
  expected.
- **Update did not add `fly.toml`** — ignore policy. Copy the file once.
- **Expo-only Docker build mentions webapp** — recreate or restore `# m5k:webapp`
  markers so create/update can strip those stages.
