# Match query in 0.33.0

:::note Open question
Confirm the published release number before linking this guide from release
notes. Packages in the monorepo currently report `0.32.9`; rename the file and
`migration.id` / `target_version` if the ship version differs from `0.33.0`.
:::

## Summary

List query `filters` stay QueryFilter UI clauses (`columnId`, `type`, `method`,
`value`). That dialect is awkward in Services: every predicate needs `type` and
`method`, there is no `$or`, and `greater_than` is not SQL `$gt`.

This release adds a **parallel Match query** stack. QueryMatch is a Mongo-style
object (`{ status: "published" }`, `{ age: { $gt: 18 } }`, `$and` / `$or` /
`$not`). Table UI and URL state stay QueryFilters. List hooks also emit a
QueryMatch. You pass `filters` to `queryList` or `match` to `matchList`.

Existing List query Procedures keep working. Starter is not migrated. Opt in
per Procedure.

How to write QueryMatch:
[List query and Match query](/guides/list-query-and-match-query).

## Who needs this migration

- **No action required** to upgrade if you keep calling `queryList` /
  `queryFind` / `.addFilters` with `input.list`. Extra `match` on the hook
  payload is stripped by List Zod.
- **Service authors** who want `$or`, strict `$gt`, or `{ field: value }`
  equality should opt Procedures in (Conditional below).
- **Table-backed lists** already send both `filters` and `match` after the
  frontend bump; you only change the Procedure you want on Match query.

## Prerequisites and upgrade order

1. Finish earlier framework migrations your app still needs
   ([member ownership](/guides/v0.32.0-memberid-ownership-migration) if you
   stamp org lists with `memberId`).
2. Upgrade `@m5kdev/commons`, `@m5kdev/backend`, and `@m5kdev/frontend`
   together to the `0.33.0` line. Do not mix with an older commons (the
   `queryMatch` export lives there).
3. Rebuild or reinstall so Jest/Node resolve commons `dist` if you consume
   workspace packages.
4. Leave List query Procedures as they are, or opt them in one at a time.

There is **no** `create-m5kdev` registry transform. The production registry
stays empty. Every application step is **Manual** or **Conditional**.

## Migration steps

### 1. Upgrade packages — Manual

Install the `0.33.0` line of `@m5kdev/commons`, `@m5kdev/backend`, and
`@m5kdev/frontend` together. `m5kdev update` does not perform this bump.

In a workspace that depends on package `dist`, rebuild commons:

```sh
pnpm --filter @m5kdev/commons build
```

### 2. Confirm List query still works — Manual

Existing list Procedures need no edits. After the frontend bump, table hooks
send `{ filters, match, page, … }`. `input.list` (`querySchema`) strips
`match`. `queryList` behaviour is unchanged.

### 3. Opt a Procedure into Match query — Conditional

Do this per list Procedure that should author QueryMatch. Swap three things
together; do not leave `queryList` reading `input.match` or `.addMatch` feeding
`queryList`.

**Before (List query):**

```ts
list = this.procedure("list")
  .input(itemSchemas.input.list)
  .output(itemSchemas.output.list)
  .requireAuth("organization")
  .addContextFilter(["member", "organization"])
  .handle(({ input }) =>
    this.repository.item.queryList(input, {
      globalSearchColumns: ["name"],
    })
  );
```

**After (Match query):**

```ts
list = this.procedure("list")
  .input(itemSchemas.input.matchList)
  .output(itemSchemas.output.list)
  .requireAuth("organization")
  .addMatch(({ match, ctx }) => ({
    ...match,
    memberId: ctx.actor.memberId,
    organizationId: ctx.actor.organizationId,
  }))
  .handle(({ input }) =>
    this.repository.item.matchList(input, {
      globalSearchColumns: ["name"],
    })
  );
```

Notes:

- `itemSchemas.input.matchList` is already on `createZodSchemas(table)` after
  the bump. You do not add a shared-contract schema unless you wrap the DTO.
- `.addMatch` is a map: return the next QueryMatch. Spread to extend. Calling
  it twice throws.
- Replace `.addContextFilter` with `.addMatch` on Match query Procedures.
  `.addContextFilter` still writes QueryFilters and only belongs on List query.
- tRPC `.input(itemSchemas.input.list)` must move to `matchList` if that
  router validates the Procedure input.

### 4. Rewrite Service-authored QueryFilters — Conditional

Only on Procedures you opted in. Convert hand-written QueryFilter arrays to
QueryMatch. Do not keep assembling `{ columnId, type, method, value }` for
equality.

```ts
// before — List query
.addFilters(() => ({
  columnId: "status",
  type: "enum",
  method: "equals",
  value: "published",
}))

// after — Match query
.addMatch(({ match }) => ({ ...match, status: "published" }))
```

Use `$gt` when you want strict greater-than. Converted table filters use
`$greater_than` (gte). See
[List query and Match query](/guides/list-query-and-match-query).

### 5. Leave table UI and URL state alone — Manual

Do not serialize QueryMatch into `nuqs`. `additionalFilters` stay QueryFilters.
The hook includes them in the emitted QueryMatch.

## Database migration

None. Predicates are request-time SQL. No schema, backfill, or Drizzle
migration.

## Environment and deployment changes

None. No new environment variables, workers, or rollout order. Backend and
frontend should deploy the matching `@m5kdev/*` versions together so a Match
query Procedure is not served by an old frontend that omits `match` (empty
`match` is a valid no-op; the risk is only if you *require* client predicates
and forget the frontend bump).

## Verification

- Typecheck the app after the package bump.
- A Procedure still on `input.list` + `queryList` returns the same rows for
  representative table filters as before.
- An opted-in Procedure: table filters still apply (hook `match`); `{ age: { $gt: 18 } }` excludes `18` while a converted `$greater_than` includes it; unknown column names return `BAD_REQUEST` instead of the unfiltered list.
- `.addMatch(({ match }) => ({ ...match, memberId }))` scopes rows when the
  client sent no `match`.
- URL filter widgets still round-trip QueryFilters.

Suggested commands (adjust to the app):

```sh
pnpm install
pnpm check-types
pnpm test
```

## Rollback

- **Application code:** revert opted-in Procedures to `input.list`,
  `.addFilters` / `.addContextFilter`, and `queryList`. List Zod ignores
  leftover `match`.
- **Packages:** pin the previous `@m5kdev/*` line. No database rollback.
- Hook-emitted `match` on an old backend is ignored by `querySchema`.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Unfiltered list after a typo in `match` | You expected List query’s silent skip | Match query errors on unknown columns; fix the key |
| `$gt: 18` includes 18 | Used `$greater_than` or List `greater_than` | `$gt` is strict; `$greater_than` is gte |
| Table dates off by a day | Used `$gt` on a calendar day | Converted filters use `$after` (start of day) |
| json `$in: ["red"]` matches nothing | `$in` is SQL `IN` on the JSON text | Use `$oneOf` for token match |
| `.addMatch` twice throws | Duplicate step name | One `.addMatch` per Procedure; spread inside it |
| Context scope missing on Match query | Left `.addContextFilter` off and did not spread in `.addMatch` | Scope with `.addMatch`; do not mix stacks |
| `queryList` ignores `input.match` | Procedure still on List query | Switch input schema + `matchList` together |
