# PostgreSQL-only persistence with pgvector

Published as michalkow/m5kdev#24 with the `ready-for-agent` label. GitHub Issues is the canonical tracker; this file is the local working copy. Implementation tickets are #25–#30, attached as native sub-issues with native blocking relationships. Implementation has started on #25 under the user's implement-spec instruction, using the four proposed public test seams.

## Problem Statement

Framework developers currently inherit Turso/libSQL and SQLite-specific persistence throughout the Kernel, Core Modules, optional modules, Starter, Database commands, tests, and scaffolding. Serialized JSON and collection-search workarounds prevent using PostgreSQL's native data representations. The AI vector integration is libSQL-specific, and Starter does not configure durable Mastra storage or Memory. Consumers need a coherent PostgreSQL-only upgrade path that also covers their own tables without silently destroying data or changing product contracts.

## Solution

Replace supported Turso/libSQL runtime persistence with PostgreSQL and pgvector throughout the stack. Use PgBouncer for runtime connections and a separate direct connection for migrations. Isolate app tables, Mastra storage, and vectors by schema within one database per app/environment. Ship persistent Starter conversations through app-owned Mastra composition, native field types and query operators, real PostgreSQL development/test infrastructure, and a copyable AI-agent migration prompt with a maintainer checklist.

8. As a framework developer, I want existing text identifiers preserved so that consumer identifiers do not need a UUID conversion.
9. As an app developer, I want structured documents stored as JSONB so that queries operate on structure instead of serialized strings.

11. As an app developer, I want relational associations to remain relational so that native-array adoption does not remove integrity constraints.
12. As an API consumer, I want native booleans and timestamps without unrelated API payload changes.
13. As a framework developer, I want supported Drizzle search operators used directly so that SQLite search-emulation helpers are removed rather than ported.

## Implementation Decisions

- This is a Kernel-wide dialect migration, not a driver substitution. Remove Turso/libSQL dependencies, configuration, replica lifecycle, retry helpers, local database files, and supported SQLite paths from runtime, tests, templates, deployment, and active docs. Historical references may remain clearly superseded. Preserve app-owned historical migration records pending an explicit maintainer baselining plan; they are not a supported runtime path.
- Preserve explicit repository/service/transport boundaries, injected dependencies, app schema composition, grants, transaction discipline, ServerResult behavior, Auth identity semantics, Workflow precedence rules, and tenancy boundaries.
- Use one database per app/environment. Default schemas are `app`, `mastra`, and `vectors`, configurable at composition roots. App migrations own framework/app tables. Mastra owns its storage structures; retain supported `mastra_` naming without patching vendor internals.
- `DATABASE_URL` is the runtime PgBouncer connection. `DATABASE_DIRECT_URL` is required for Drizzle migrations and administrative initialization; no silent runtime-URL fallback. Keep credentials server-only. Distinct roles may point at identical endpoints where appropriate.
- Target PgBouncer transaction pooling and share the application pool across repositories. Qualify database objects explicitly; implementation must verify session-state, prepared-statement, adapter, and shutdown requirements rather than relying on connection affinity.
- Select and pin compatible PostgreSQL, pgvector, driver, Drizzle, Better Auth, and Mastra adapter versions using primary-source documentation and installed package APIs. No unsupported dependency upgrade or unverified adapter capability is assumed by this spec.
- Use JSONB for documents, native arrays for genuine homogeneous scalar collections, native booleans, and timezone-aware timestamps for instants. Keep identifiers as text and association tables relational. Audit defaults, nullability, unique constraints, foreign keys, indexes, serializers, API contracts, and raw SQL individually.
- Remove SQLite serialized-text JSON/array search emulation and redundant operator wrappers. Use supported Drizzle operators directly. Retain necessary QueryFilter/QueryMatch translation, not an imitation of database functionality. If a required JSONB operator has no supported Drizzle helper, use a narrow parameterized PostgreSQL expression and document that limitation.
- Preserve intended text-search case sensitivity and escaping; use structural collection semantics. Document intentional changes instead of preserving serialized-text bugs.
- Provision pgvector and run application migrations before runtime startup. Perform required Mastra initialization separately using its supported lifecycle. Startup checks readiness and reports actionable failures; it does not silently migrate application tables.
- Configure durable Mastra storage and Conversation Memory in Starter while keeping composition app-owned. Preserve personal UserId Thread-resource behavior; do not introduce new tenancy semantics or revive legacy chat blobs.
- Preserve current embedding/upsert capabilities. Keep model, dimensions, and distance metric explicit and app-owned; validate dimensions. Additional connection pools owned by adapters require explicit lifecycle ownership and cleanup.
- Remove replica `sync` and its scripts. Keep explicit migration/seed/reset operations. Reset touches only the app-owned schema, requires an explicit disposable-environment declaration, and does not implicitly delete Mastra or vector schemas. Database command implementations stay Kernel-owned and HTTP-free; migration history stays app-owned.
- Provide reproducible real PostgreSQL+pgvector local and CI environments, including runtime pooling validation and isolated integration/E2E data. No SQLite test substitute.
- Publish a copyable AI-agent prompt and maintainer checklist covering all framework/app tables, native-type mappings, repository/query changes, migration generation, source-to-target data transfer, validation, cutover, rollback, secrets, and removal of obsolete dependencies/configuration. The prompt does not authorize blanket resets, arbitrary migrations, or a universal zero-downtime procedure.
- Deliver one coordinated breaking release, all publishable packages in lockstep. Select its exact version during release preparation; do not publish packages as part of implementation without instruction.

## Testing Decisions

Proposed seams requiring user confirmation before tests are authored:

1. Starter/Kernel public application behavior, including Auth, repository List/Match behavior, transactions, Workflow write-behind precedence, readiness, and lifecycle, against real PostgreSQL. Extend existing repository, Kernel, Auth, and Workflow integration-test patterns rather than asserting private helper calls.
2. The public Database command/configuration boundary: runtime versus direct URL selection, absent direct configuration, seed, guarded reset, app-schema isolation, and rejected sync. Extend the existing Database-command tests and verify through public APIs where available.
3. Public Conversation/AI behavior using configured Mastra storage and pgvector: history across restart, personal resource isolation, supported embedding upserts, dimension mismatch, and lifecycle ownership. Extend existing AI/Conversation tests; avoid mocking away PostgreSQL semantics.
4. Generated Starter operational smoke behavior: install/build/typecheck and startup against prepared PostgreSQL, plus existing E2E flows. Use existing scaffold/E2E seams rather than snapshotting implementation structure.

Use red-green tracer bullets, one behavior at a time. Mock external model providers and remote product services when necessary, not the database dialect. Include worked examples for empty/null arrays, quoted and escaped elements, JSON objects, scalar membership, timestamps/timezones, search wildcards, and non-UUID IDs. Final validation includes repository typechecks, targeted and broader relevant tests, generated-template checks, and active-source dependency/configuration removal audits. Do not claim integration success without executing against the required infrastructure.

## Out of Scope

- Dual SQLite/PostgreSQL support, embedded replicas, and SQLite local/test fallbacks.
- New retrieval APIs, embedding-model changes, automatic re-embedding, approximate-index tuning, or a new RAG product feature.
- New tenancy or authorization models, identifier normalization to UUIDs, unrelated API redesign, and replacing Redis/BullMQ.
- Agent-generated Drizzle migrations, migration metadata, production data deletion, live cutover execution, or deployment credential collection.
- Package publication or an invented release number.

## Further Notes

The accepted architectural decisions are recorded in ADR-0033; ADR-0002, ADR-0004, ADR-0005, ADR-0007, and ADR-0018 remain applicable. Exact adapter capabilities and field mappings are implementation verification gates, not additional product-design interviews.

The repository requires maintainer-generated migrations. When schema changes require them, stop and ask the maintainer to run the project generation command after the PostgreSQL schema/configuration is ready; do not edit old SQLite history to fake a PostgreSQL baseline. Implementation is not complete until the maintainer-generated artifacts and database setup permit integration verification.

The current checkout already has a PostgreSQL migration integration branch. Keep one checkout and implement the ticket frontier sequentially. No commit, PR, or tracker completion is assumed to have happened merely because this draft exists.
